# Асинхронность и конкурентность

Детализация секции 5 из [JSTS.md](./JSTS.md). Пункты **81–105**.

Конспект для собеседования: в каждой теме сначала **о чём речь и зачем спрашивают**, потом устройство, ловушки и TypeScript.

### 81. Call stack, heap, queue

О чём речь: JavaScript в одном агенте (вкладка, worker) выполняет синхронный код по одному кадру за раз. Пока кадр не вернулся, следующий колбэк из очереди не начнётся. На Senior это спрашивают, чтобы отличить «код завис» от «код ждёт очередь», объяснить `Maximum call stack size exceeded` и понять, почему длинный цикл блокирует клики и таймеры.

Спека говорит про **стек контекстов выполнения**. Движок реализует его как call stack. Объекты и функции живут в куче, сборщик мусора забирает недостижимое. Колбэки ждут в очередях, их забирает event loop (п. 82), когда стек пуст.

---

#### Стек вызовов

Вызов функции кладёт кадр: куда вернуться, локальные имена, аргументы. `return` кадр снимает. Вложенный вызов кладёт кадр сверху. Смотреть «кто кого позвал» — это и есть стек, его печатает `Error.stack`.

```js
function a() {
  b();
}
function b() {
  c();
}
function c() {
  console.log("here");
}
a();
// кадры сверху вниз в момент console.log: c → b → a → глобальный/модульный кадр
```

Рекурсия без дна растит стек, пока движок не бросит `RangeError`. Хвостовой вызов в JS не оптимизируют (п. 64): даже «хвостовая» рекурсия занимает кадр.

Пока верхний кадр жив, очередь не двигается. Цикл на миллион итераций, синхронный `JSON.parse` большого файла, тяжёлый рендер без паузы — страница не обработает клик, хотя таймер «уже пора». Таймер записан в очередь, стек занят.

---

#### Куча

Кадр хранит ссылку. Сам объект, массив, функция и замыкание (п. 33) лежат в куче. Когда кадр сняли, объект жив, пока на него есть ссылка: из другого объекта, из замыкания, из очереди колбэков.

```js
function make() {
  const big = new Array(1_000_000).fill(1);
  return () => big.length;
}
const keep = make(); // кадр make уже снят, big жив: его держит замыкание keep
```

`keep = null` снимает последнюю ссылку, массив может быть собран. Колбэк в `setTimeout` — тоже ссылка: пока таймер не сработал или его не сняли `clearTimeout`, замыкание не мусор.

Примитив в локальной переменной может жить в кадре. Это деталь движка, на неё код не опирается. Для модели достаточно: имена кадра указывают на значения, объекты — в куче.

---

#### Очереди

Очередь — не один список. Есть очереди **задач** (macrotask: таймер, I/O, клик) и очередь **микрозадач** (промисы, `queueMicrotask`). Подробное сравнение — п. 83. Здесь важно правило порядка:

1. Выполнить текущий синхронный код до пустого стека.
2. Вычерпать микрозадачи, которые этот код успел поставить, снова до пустой очереди.
3. Взять одну следующую задачу (таймер, событие).
4. Повторить.

```js
console.log("sync");
setTimeout(() => console.log("task"), 0);
console.log("still sync");
// sync
// still sync
// task
```

`setTimeout(..., 0)` не вставляет колбэк «прямо сейчас». Он ставит задачу. Она стартует, когда стек текущего хода пуст и микрозадачи тоже пусты.

---

#### Ловушка: отдать управление, не уронив стек

Бесконечная рекурсия падает. Тот же обход, отложенный задачей, стек не растит: каждый кусок начинается с пустого стека.

```js
function walk(n) {
  if (n === 0) return;
  console.log(n);
  setTimeout(() => walk(n - 1), 0);
}
walk(3);
// 3, потом 2, потом 1 — между ними цикл успевает взять другие задачи
```

Цена: между шагами вклиниваются чужие колбэки, порядок «сразу всё» пропадает. Для длинной работы на главном потоке позже есть `scheduler.yield` (п. 105). Второй стек в том же окне так не получить: параллельный стек — это другой агент, worker (п. 96).

---

#### Сводка

| | Что хранит | Когда пустеет |
|---|---|---|
| Стек | кадры текущего синхронного захода | `return` / конец обработчика |
| Куча | объекты, функции, замыкания | нет ссылок → GC |
| Очередь задач | таймеры, I/O, ввод | event loop берёт по одной, когда стек пуст |
| Очередь микрозадач | реакции промисов | сразу после текущего стека, до следующей задачи |

В новом коде длинную синхронную работу режут на куски или уносят в worker. Рекурсию по глубокому дереву не оставляют «как есть» на главном потоке.

#### TypeScript

Стек, куча и очереди на типы не влияют: это рантайм. `Error.stack` — строка, тип её не разбирает. Source map привязывает кадры к `.ts`, но сам стек остаётся стеком JS после emit. Тип `Promise` ничего не говорит о том, занят ли стек.

Что сказать на собеседовании: один агент — один стек. Пока кадр жив, очереди ждут. Объекты в куче, кадр держит ссылку. `setTimeout(0)` — это задача после текущего стека и микрозадач, не «следующая строка». Глубокая рекурсия — `RangeError`, не event loop.

### 82. Event loop: browsers vs Node (phases)

О чём речь: event loop забирает готовую работу, когда стек пуст. В браузере это цикл HTML: задача, микрозадачи, иногда отрисовка. В Node это фазы libuv плюс отдельные очереди `process.nextTick` и промисов. На собеседовании путают «один рисунок на все среды» и обещают фиксированный порядок `setTimeout(0)` и `setImmediate`.

---

#### Браузер

У окна (и у worker) свой цикл. Задачи лежат в нескольких очередях по источникам: таймеры, сеть, пользовательский ввод, парсинг. Цикл выбирает очередь и берёт **одну** задачу. Это не одна общая FIFO на всё: источник «клик» и источник «таймер» спека не сливает в один список.

Ход такой:

1. Выполнить выбранную задачу до конца.
2. Вычерпать очередь микрозадач.
3. Если пора рисовать — `requestAnimationFrame`, стиль, layout, paint (п. 95).
4. Снова выбрать задачу.

Пока микрозадачи не кончились, кадр не нарисуют. Цепочка `then`, которая сама ставит `then`, держит отрисовку. Node рисовать нечему: шага paint нет.

`setTimeout(fn, 0)` в браузере не равен 0 мс. После нескольких вложенных таймеров HTML зажимает задержку минимум до 4 мс. Фоновая вкладка зажимает сильнее. `setInterval` не запускает второй колбэк, пока предыдущий ещё на стеке: параллельных тиков нет, интервал плывёт.

---

#### Фазы Node

Node крутит цикл libuv. Картинка из документации, сверху вниз, потом снова timers:

| Фаза | Что выполняет |
|---|---|
| timers | `setTimeout`, `setInterval`, срок которых уже наступил |
| pending callbacks | часть отложенных системных колбэков (ошибки TCP и похожее) |
| idle, prepare | внутреннее, в прикладном коде её нет |
| poll | забрать I/O; если ждать нечего и таймеры ещё не готовы, здесь цикл может заблокироваться |
| check | `setImmediate` |
| close callbacks | например `socket.on("close")` |

`process.nextTick` **не фаза**. После текущего куска JS Node сначала опустошает очередь nextTick (включая то, что поставили уже внутри nextTick), потом микрозадачи промисов, и только затем продолжает фазу. Рекурсивный `nextTick` не отдаёт цикл I/O: фазы стоят.

С Node 11 микрозадачи бегут между колбэками таймеров, ближе к браузеру. Раньше вся фаза timers могла отработать до промисов. На современный Node старые статьи про «сначала все таймеры» не опираться.

---

#### Ловушка: `setTimeout(0)` и `setImmediate`

На верхнем уровне модуля порядок этих двух **не зафиксирован**: старт цикла может попасть в timers раньше poll или наоборот.

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
// какой из двух логов первый — гадать нельзя
```

Внутри колбэка I/O порядок стабильный: poll уже идёт, следующая фаза — check, таймеры только на следующем круге.

```js
const fs = require("fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
// immediate
// timeout
```

В браузере `setImmediate` нет (старый IE не в счёт). Аналог «после текущего I/O» собирают через `MessageChannel` (п. 94). `process.nextTick` в браузере тоже нет: ближайшее «после стека, но до таймера» — `queueMicrotask`.

Отдельный порядок только Node:

```js
process.nextTick(() => {
  console.log("nt1");
  process.nextTick(() => console.log("nt2"));
  Promise.resolve().then(() => console.log("p"));
});
Promise.resolve().then(() => console.log("p0"));
// nt1, nt2, p0, p
```

Очередь nextTick вычерпывается целиком до промисов. `p0` уже стоял в микрозадачах, но ждёт конца nextTick. Новый nextTick (`nt2`) обгоняет и старый промис, и промис, поставленный из `nt1`.

---

#### TypeScript

Цикл на типы не влияет. Расходится объявление таймера: в DOM `setTimeout` возвращает `number`, в `@types/node` — `NodeJS.Timeout`. Один и тот же файл, собранный с `lib: ["dom"]` и типами Node, ловит конфликт на `clearTimeout(id)`. Лечат отдельным типом проекта под среду (п. 121, п. 124), не `as any` на каждый таймер. `setImmediate` и `process.nextTick` есть только в типах Node. В браузерном проекте их быть не должно: компилятор как раз ловит среду.

Что сказать на собеседовании: браузер — задача, микрозадачи, иногда paint. Node — фазы libuv; nextTick и промисы между операциями, nextTick раньше промисов и сам не фаза. `setTimeout(0)` против `setImmediate` наверху не определён, внутри I/O первым идёт `setImmediate`. Таймер в типах — `number` в DOM и объект в Node.

### 83. Macrotasks vs microtasks

О чём речь: задача (macrotask) — один заход цикла: таймер, клик, I/O, `setImmediate`. Микрозадача — реакция, которую надо доделать до следующей задачи и до отрисовки: `then`/`catch`/`finally`, `await`, `queueMicrotask`, в браузере ещё `MutationObserver`. Путаница на собеседовании: «`setTimeout(0)` выполнится следующим» и код, который микрозадачами никогда не отдаёт кадр.

---

#### Кто в какой очереди

Задача ставится в очередь источника и ждёт, пока цикл до неё дойдёт. Между двумя задачами стек пуст, микрозадачи уже вычерпаны, браузер мог нарисовать кадр.

Микрозадача ставится в одну очередь и бежит, как только текущий стек опустел, **раньше** любой уже стоящей задачи. Новые микрозадачи, поставленные по ходу, встают в хвост той же очереди и тоже бегут в этом заходе. Задача из `setTimeout` внутри `then` не вклинивается между микрозадачами: она ждёт следующего выбора задачи.

`process.nextTick` в Node — третья, более ранняя очередь (п. 82). В браузере её нет. `requestAnimationFrame` не микрозадача и не обычный таймер: слот перед paint.

`queueMicrotask(fn)` ставит микрозадачу напрямую. `Promise.resolve().then(fn)` делает то же через реакцию промиса, но ещё создаёт промис. Для «просто после стека» достаточно `queueMicrotask`.

---

#### Порядок на одном примере

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => {
  console.log(3);
  setTimeout(() => console.log(4), 0);
});
queueMicrotask(() => console.log(5));
console.log(6);
// 1
// 6
// 3
// 5
// 2
// 4
```

Синхронный код печатает 1 и 6 и ставит: задачу «2», микрозадачу «3», микрозадачу «5». Стек пуст. Микрозадачи по порядку постановки: 3, затем 5. Внутри «3» ставится вторая задача «4». Задачи ещё не начинались. Потом цикл берёт «2», потом «4».

`async`-функция до первого `await` — это синхронный код. Продолжение после `await` — микрозадача, даже если ждали уже готовое значение или `await null` (п. 87).

---

#### Ловушка: голодание задач

Микрозадачи вычерпывают до конца. Цикл, который сам ставит микрозадачу, не дойдёт ни до таймера, ни до paint.

```js
function spin() {
  queueMicrotask(spin);
}
spin();
setTimeout(() => console.log("never soon"), 0);
// "never soon" не печатается, пока spin крутится: каждая микрозадача ставит следующую
```

То же делает цепочка `Promise.resolve().then(spin)` и рекурсивный `nextTick`. Симптом в браузере — замерший ввод. Лечение: шаг, который можно отложить, ставить задачей (`setTimeout`, `setImmediate`, пост-сообщение), а микрозадачей оставлять короткое «доделать текущий ход».

Вторая ловушка — ждать от `setTimeout(fn, 0)` место «сразу после этой строки». Перед ним отработают все микрозадачи, и задержка снизу ещё зажата браузером (п. 82).

---

#### Сводка

| | Примеры | Когда бежит | Может забить цикл |
|---|---|---|---|
| Синхронный код | тела функций, executor промиса | сразу, кадр стека | да, длинный кадр |
| Микрозадача | `then`, `await`, `queueMicrotask` | после стека, до следующей задачи | да, если ставит себя |
| Задача | таймер, клик, I/O, `setImmediate` | когда цикл выбрал её | одна задача не отменяет остальные, но долго занимает стек |
| nextTick (только Node) | `process.nextTick` | раньше микрозадач | да |

#### TypeScript

Очереди стираются: тип колбэка ничего не говорит, микро это или задача. `queueMicrotask` в типах DOM и Node возвращает `void`. `Promise.then` типизирован как цепочка (п. 84), и это легко прочитать как «выполнится по порядку строк». Порядок строк и порядок очередей — разное, компилятор второе не проверяет.

Что сказать на собеседовании: синхронный код, потом вся очередь микрозадач, потом одна задача. `then` обгоняет уже поставленный `setTimeout(0)`. Микрозадача, которая ставит микрозадачу, не отдаёт отрисовку. `await` — продолжение микрозадачей, не новой задачей.

### 84. `Promise` states, chaining, `thenable`

О чём речь: промис — ячейка будущего значения. Она один раз переходит из ожидания в успех или в отказ и больше не меняется. `then` не «подписывается на тот же объект как на EventEmitter ради нового состояния», а возвращает **новый** промис. На собеседовании ломаются на проглоченной ошибке, на забытом `return` и на объекте с случайным методом `then`.

---

#### Состояния

Три состояния: `pending`, `fulfilled`, `rejected`. Вместе fulfilled и rejected называют settled. Повторный `resolve` / `reject` игнорируется: побеждает первый.

```js
const p = new Promise((resolve, reject) => {
  resolve(1);
  resolve(2);
  reject(new Error("no"));
});
p.then((v) => console.log(v)); // 1
```

Executor (`(resolve, reject) => ...`) выполняется **синхронно**, в том же стеке, где вызвали `new Promise`. Успех или отказ колбэков `then` — уже микрозадачи, даже если промис к этому моменту settled.

`reject` и `throw` внутри executor оба переводят промис в rejected. `throw` после `resolve` уже ни на что не влияет: состояние запечатано, исключение из executor после settle не всплывает вторым отказом.

---

#### Цепочка

`p.then(onOk, onErr)` возвращает новый промис. Его состояние решает то, что сделал обработчик:

- вернул обычное значение — новый промис fulfilled с ним;
- вернул промис или thenable — новый ждёт его и повторяет его итог;
- бросил — новый промис rejected.

```js
Promise.resolve(1)
  .then((n) => n + 1)
  .then((n) => Promise.resolve(n + 1))
  .then((n) => console.log(n)); // 3
```

Обработчик отказа **чинит** цепочку, если сам вернул значение. Дальше идёт успех, не отказ.

```js
Promise.reject(new Error("boom"))
  .then(
    () => console.log("ok"),
    () => "recovered",
  )
  .then((v) => console.log(v)); // "recovered"
```

Второй аргумент `then` ловит отказ **входного** промиса. Отказ, родившийся внутри первого обработчика, идёт уже в промис, который `then` вернул. Его этим же вторым аргументом не поймать.

```js
Promise.resolve(1).then(
  () => {
    throw new Error("inside");
  },
  (e) => console.log("no", e),
);
// "no" не печатается. Отказ у следующего звена.
// Ловят следующим .catch(...) или вторым then ниже по цепочке.
```

`catch(fn)` — это `then(undefined, fn)`. `finally(fn)` выполняет побочный шаг и **пробрасывает** прежнее значение или отказ. `return 1` из `finally` не подменяет успех. `throw` или возврат отклонённого промиса из `finally` подменяет итог отказом.

Забытый `return` обрывает ожидание внутреннего промиса: наружу уходит `undefined`, работа внутри ещё едет.

```js
function load() {
  fetch("/user").then((r) => r.json()); // промис fetch никто не вернул
}
load().then((data) => console.log(data)); // TypeError: load() — undefined, не промис
```

Нужно `return fetch(...).then(...)`.

---

#### Thenable

`Promise.resolve(x)` ведёт себя так:

- если `x` уже native `Promise` этого конструктора — вернёт тот же объект;
- если у `x` есть метод `then` — снимет значение через него (thenable);
- иначе завернёт `x` в успешный промис.

```js
const thenable = {
  then(resolve) {
    resolve(1);
  },
};
Promise.resolve(thenable).then((v) => console.log(v)); // 1
```

Чужая thenable принимается в микрозадаче: даже «готовый» объект с `then` не читается синхронно до конца.

---

#### Ловушка: лишний `then`

Любой объект с `then` для `Promise.resolve` и для `await` — не значение, а источник промиса. Если `then` не вызывает ни `resolve`, ни `reject`, внешний промис висит вечно.

```js
const user = {
  name: "Ada",
  then() {
    /* забыли resolve */
  },
};
Promise.resolve(user).then(() => console.log("nope"));
// тишина: user восприняли как thenable
```

Так тонут ответы API и старые библиотеки, где `then` случайно оказался методом. Перед `Promise.resolve` на чужой объект смотрят, точно ли это промис, а не «данные с полем then». Класс-промис из другой копии библиотеки (два realm, два бандла) может не пройти проверку `instanceof` и уйти в ветку thenable — обычно всё равно сработает, но идентичность «тот же объект» уже не гарантирована.

---

#### TypeScript

`Promise<T>` стирается до обычного промиса. `resolve` в конструкторе принимает `T | PromiseLike<T>`, поэтому внутрь можно отдать и значение, и thenable. `reject` в типах lib принимает `any`: отказ намеренно не типизируют как `T`.

`PromiseLike<T>` — структурный «есть `then`». Его возвращают чужие библиотеки. `await` разворачивает и `Promise`, и thenable; тип развёртки — `Awaited<T>` (п. 136, глубоко не здесь). Аннотация `Promise<User>` на результате `JSON.parse` ничего не проверяет в рантайме (п. 79): компилятор верит вам.

Что сказать на собеседовании: состояние одно и навсегда, executor синхронный, `then` всегда новый промис. Возврат промиса из `then` вкладывается, `throw` отклоняет следующее звено, второй колбэк `then` не ловит ошибку первого. Объект с `then` — thenable, `Promise.resolve` может на нём зависнуть. `finally` не подменяет успешное значение.

### 85. `Promise.all` / `allSettled` / `race` / `any`

О чём речь: четыре комбинатора ждут не один промис, а набор. Отличаются тем, **когда** наружный промис завершается и **что** в нём лежит: первое успешное значение, первый итог вообще, массив успехов или массив исходов. На собеседовании путают `all` и `allSettled`, забывают, что проигравшие промисы не отменяются, и не знают, что `race([])` висит навсегда.

Порядок элементов результата у `all` и `allSettled` — порядок **входа**, не порядок финиша.

---

#### `Promise.all`

Успех, когда успешен каждый. Отказ — на первом отказе, с его причиной, не дожидаясь остальных. Пустой список даёт успешный `[]`.

```js
const slow = new Promise((resolve) => {
  setTimeout(() => {
    console.log("slow done");
    resolve(1);
  }, 50);
});

try {
  await Promise.all([slow, Promise.reject(new Error("fast"))]);
} catch (e) {
  console.log(e.message); // "fast" — сразу
}
// позже всё равно "slow done": slow никто не остановил
```

Остальные запросы, таймеры и записи в базу после отказа `all` продолжаются. Отмена — отдельно, сигналом (п. 89).

---

#### `Promise.allSettled`

Ждёт каждый исход. Наружу почти всегда успех: массив `{ status: "fulfilled", value }` или `{ status: "rejected", reason }`. Синхронный бросок **до** вызова комбинатора `allSettled` не ловит — до него код просто не дошёл.

Пустой список — успешный `[]`. Удобно для пачки независимых операций, где частичный провал — нормальный результат, а не повод бросить всю пачку.

```js
const rows = await Promise.allSettled([
  Promise.resolve("a"),
  Promise.reject(new Error("b")),
]);
// rows[0].status === "fulfilled"
// rows[1].status === "rejected"
```

---

#### `Promise.race` и `Promise.any`

`race` завершается как первый settled: и успех, и отказ. Остальные продолжают работать. Пустой список **не завершается никогда**: ждать нечего, отказывать спека не велит.

`any` ждёт первый **успех**. Отказы копит. Если отказов не осталось и успеха не было — отказ с `AggregateError`, поле `errors`. Пустой список сразу даёт `AggregateError`.

```js
await Promise.any([
  Promise.reject(new Error("a")),
  Promise.resolve("ok"),
]);
// "ok"

try {
  await Promise.any([Promise.reject(1), Promise.reject(2)]);
} catch (e) {
  console.log(e instanceof AggregateError); // true
  console.log(e.errors); // [1, 2]
}
```

`race` с таймаутом (п. 90) отвечает «кто первый», но не отменяет медленную работу. `any` для «первый живой из зеркал» то же: проигравшие запросы ещё едут.

---

#### Ловушка: пустой `race` и общий список

```js
const pending = Promise.race([]);
// навсегда pending. Таймаут так не пишут: пустой список гонок — зависание, не мгновенный отказ.
```

Вторая дыра — сложить промисы в заранее типизированный массив и потерять, кто на какой позиции. Это уже TS, но ломает разбор результата: `all` вернёт массив одного общего типа, не кортеж.

Не-массив тоже подходит: комбинаторы принимают iterable. `Promise.all(new Set([p1, p2]))` работает. Генератор промисов запустит их в момент обхода, то есть сразу внутри `all`, не лениво по одному.

---

#### Сводка

| | Успех | Отказ | Пустой вход | Проигравшие |
|---|---|---|---|---|
| `all` | все успешны, значения по порядку входа | первый отказ | `[]` | продолжают работу |
| `allSettled` | всегда (если дошли до вызова), массив исходов | почти не отказывает | `[]` | все как раз и нужны |
| `race` | первый settled, если это успех | первый settled, если это отказ | висит | продолжают |
| `any` | первый успех | все отказали, `AggregateError` | сразу `AggregateError` | продолжают |

#### TypeScript

У литерала массива `Promise.all([a, b])` сохраняет кортеж: первая позиция — тип `a`, вторая — тип `b`. Если сначала записать промисы в `Promise<string | number>[]`, обе позиции станут `string | number`.

```ts
declare function fetchName(): Promise<string>;
declare function fetchAge(): Promise<number>;

const [name, age] = await Promise.all([fetchName(), fetchAge()]);
// name: string, age: number

const list: Promise<string | number>[] = [fetchName(), fetchAge()];
const [x, y] = await Promise.all(list);
// x и y: string | number
```

`allSettled` даёт дискриминант `status`. Сужение `value` / `reason` работает после `if (row.status === "fulfilled")`. `AggregateError` в типах есть, `errors` — `any[]`: причину каждого отказа всё равно сужают самим.

Что сказать на собеседовании: `all` падает на первом отказе и не отменяет соседей. `allSettled` собирает все исходы. `race` — первый итог, пустой `race` висит. `any` — первый успех, иначе `AggregateError`. Порядок результатов — порядок аргументов. Кортеж типов живёт на литерале массива, не на широком `Promise<T>[]`.

### 86. Unhandled rejections

О чём речь: промис отклонился, а к отказу никто не подключился. Браузер шлёт `unhandledrejection`, Node с 15 версии по умолчанию валит процесс. На собеседовании это «почему `try/catch` вокруг вызова не поймал» и «почему `.catch` на следующей задаче уже поздно».

Отказ считается необработанным, если к моменту, когда цикл фиксирует отказ, у промиса нет обработчика отказа. Подключить `.catch` синхронно, в том же заходе, где промис создали, — успеть можно. Подключить на следующем таймере — событие уже ставится.

---

#### Где слушают

Браузер: `window` / `self`, событие `unhandledrejection`. В `event.reason` причина, в `event.promise` сам промис. `preventDefault()` говорит hosts, что отказ заметили. Если обработчик повесили позже, приходит `rejectionhandled`.

Node: `process.on("unhandledRejection", (reason, promise) => ...)`. С Node 15 молчаливый отказ по умолчанию бросает и процесс завершается с ненулевым кодом. До 15 был warning, процесс жил. Режим крутят флагом `--unhandled-rejections=throw|strict|warn|none`. Свой слушатель не заменяет дисциплину: отказ всё равно надо обработать у промиса, логгер на процессе — последняя сетка, не бизнес-логика.

---

#### Что считается обработкой

`.catch`, второй аргумент `.then`, `await` внутри `try/catch`, `finally` на **этом** промисе. `finally` помечает исходный промис обработанным и возвращает **новый**. Если исходный был rejected, новый тоже rejected. Его снова нужно поймать, иначе необработан уже он.

```js
Promise.reject(new Error("x")).finally(() => {
  console.log("cleanup");
});
// cleanup будет
// промис, который вернул finally, отклонён с "x" и сам по себе не обработан
```

`try/catch` ловит только синхронный бросок. Вызов `async`-функции синхронно возвращает промис, бросок внутри него в этот `catch` не попадает.

```js
async function fail() {
  throw new Error("later");
}

try {
  fail(); // промис выбросили, не await
} catch (e) {
  console.log("no"); // не выполнится
}
// отказ fail всплывёт как unhandled rejection
```

То же с `fetch().then(...)` без `return` / `await` / `.catch`: цепочка есть, а наружу её никто не держит.

---

#### Ловушка: поздно повешенный `catch`

```js
const p = Promise.reject(new Error("x"));

setTimeout(() => {
  p.catch(() => {}); // отказ уже заметили как необработанный
}, 0);
```

В том же синхронном заходе `p.catch(...)` событие обычно гасит: обработчик появился до фиксации. `queueMicrotask(() => p.catch(...))` часто тоже успевает, потому что уведомление — отдельная задача после микрозадач. На следующую задачу не рассчитывают: это уже гонка с хостом.

Паттерн «запустить и забыть» без сетки — дыра. Если намеренно не ждут результат, отказ всё равно ловят: `void save().catch(log)`.

---

#### TypeScript

Строгий `tsc` **не** считает висящий промис ошибкой. `no-floating-promises` (typescript-eslint) как раз требует `await`, `return` или `void`. `void promise` — пометка «я специально не жду». Сам `void` отказ не обрабатывает: без `.catch` это всё ещё unhandled rejection, только линтер молчит.

```ts
async function run(): Promise<void> {
  save(); // линтер: floating promise. Типы молчат: run всё равно Promise<void>
}
```

`no-misused-promises` ловит смежное: `async`-предикат в `if`, промис там, где ждали `void` колбэк. Аннотация функции как `Promise<void>` не заставляет вызвать внутренние промисы.

Что сказать на собеседовании: отказ без обработчика — событие в браузере и с Node 15 падение процесса. `try/catch` без `await` не ловит. `.catch` на следующем таймере уже поздний. `finally` гасит исходный промис и может отдать новый необработанный отказ. `void` для линтера — не обработка ошибки.

---

### 87. `async` / `await`, desugaring, error boundaries

О чём речь: `async`-функция всегда возвращает промис. `await` разворачивает промис в значение или бросает отказ в эту функцию, как `throw`. Это сахар над цепочкой `then`, с одним важным следствием: граница `try/catch` стоит там, где написан `await`, а не там, где функцию просто вызвали. На собеседовании показывают два `await` подряд и спрашивают, почему второе ждёт первое, и почему React error boundary не видит отказ из `useEffect`.

---

#### Что делает `async`

До первого `await` тело идёт синхронно. `return x` завершает возвращённый промис успехом с `x`. Если `x` сам промис или thenable, итог разворачивается, как `Promise.resolve`. `throw` отклоняет возвращённый промис.

```js
async function f() {
  console.log("a");
  await null;
  console.log("b");
}
console.log("c");
f();
console.log("d");
// c, a, d, b
```

`a` синхронно, до отдачи стека. `b` — микрозадача после `await`, даже хотя ждали `null`. Вызов `f()` синхронно вернул промис, его здесь никто не читает.

Грубое раскрытие без полного emit:

```js
function f() {
  console.log("a");
  return Promise.resolve(null).then(() => {
    console.log("b");
  });
}
```

Реальный `await` чуть строже учебника: продолжение всегда через реакцию промиса, то есть микрозадача есть даже у уже fulfilled промиса. Несколько `await` подряд — несколько таких стыков, не один общий `then` на всю функцию.

---

#### Граница ошибки

`await` на отклонённом промисе бросает в месте `await`. Обычный `try/catch` это ловит. Без `await` тот же отказ остаётся в возвращённом промисе и границу не пересекает (п. 86).

```js
async function load() {
  try {
    await a();
    await b(); // если a отказал, b не вызывается
    return "ok";
  } catch (e) {
    return "fallback";
  }
}
```

Это и есть граница: внутри `catch` отказ уже значение, наружу `load` может вернуть успешный промис. Если `catch` нет, отказ `a()` становится отказом `load()`, и ловить его должен вызывающий: `await load()` в своём `try` или `.catch`.

Вызывающий, который написал `load()` внутри синхронного `try`, границу промахнул. Два уровня:

```js
async function outer() {
  try {
    await load(); // ловит отказ load
  } catch (e) {
    console.log("boundary", e);
  }
}
```

`return await promise` внутри `try/catch` нужен, чтобы `catch` этой функции увидел отказ. Голый `return promise` из `async`-функции тоже пробросит отказ наружу, но локальный `catch` ниже `return` его уже не обернёт: возврат случился раньше.

Одна фраза про React: error boundary класса ловит отказ рендера. Отказ промиса из эффекта или обработчика в неё не всплывает, пока его самим не пробросили в состояние рендера. Граница эффекта — `try/catch` вокруг `await` или `.catch` на цепочке.

---

#### Ловушка: `await` на массиве промисов

`await` разворачивает промис, не массив. `map` с `async` возвращает массив промисов сразу, цикл колбэков стартует, а `await` перед массивом ничего не ждёт.

```js
async function saveAll(items) {
  await items.map(async (item) => {
    await write(item); // каждый write стартовал, наружный await ждал массив
  });
  console.log("not actually done");
}
```

Массив — не thenable (если только его не наделили `then`). `await` на нём продолжает функцию микрозадачей, не дожидаясь `write`. Отказы `write` при этом легко становятся необработанными. Нужно `await Promise.all(items.map(...))` или цикл `for...of` с `await` внутри, если порядок и ограничение параллелизма важны (п. 88).

Вторая ловушка — случайная последовательность там, где хотели параллель:

```js
const a = await fetchA();
const b = await fetchB(); // fetchB стартует только после fetchA
```

Параллельный старт — вызывать обе функции до `await`:

```js
const pendingA = fetchA();
const pendingB = fetchB();
const a = await pendingA;
const b = await pendingB;
```

Или `Promise.all` (п. 85).

---

#### TypeScript

Возврат `async function` в типах всегда `Promise<...>`. `return 1` при аннотации `Promise<number>` законен: компилятор знает про заворачивание. Аннотация голого `number` на `async`-функции — ошибка типа.

`await` сужает до `Awaited<T>`. На типах это разворот промиса; в рантайме это всё ещё микрозадача.

Emit зависит от `target`. При `ES2017` и новее `async`/`await` остаются в JS. При более низком target TypeScript выпускает помощник `__awaiter` и обычные промисы. Типы при этом не «включены в рантайм»: помощник — настоящий JS, дженерик `T` стёрт.

Что сказать на собеседовании: `async` возвращает промис, до первого `await` код синхронный, продолжение — микрозадача. `try/catch` ловит `await`, не голый вызов. `await array.map(async ...)` ждёт массив, не операции. Два `await` подряд — последовательность; для параллели стартуют промисы до ожидания. Ниже ES2017 в бандле будет `__awaiter`, не ключевое слово.

---

### 88. Sequential vs parallel vs pool/limit concurrency

О чём речь: пачку независимых операций можно сделать по одной, все сразу или пачками по N. «Все сразу» на Senior часто хуже «по одной»: пул соединений, лимит файловых дескрипторов, шесть соединений HTTP/1.1 на хост в браузере. Спрашивают, как написать пул без мьютекса и почему `i++` между `await` здесь не гонка.

Один агент JS не выполняет колбэки параллельно (п. 81). «Параллель» здесь значит «несколько операций уже запущены и ждут I/O», а не два стека сразу.

---

#### Последовательно

Следующая операция стартует после итога предыдущей. Мало давления на базу и предсказуемый порядок. Время — сумма времён.

```js
async function mapSeq(items, fn) {
  const out = [];
  for (const item of items) {
    out.push(await fn(item));
  }
  return out;
}
```

`forEach` с `async`-колбэком так не работает: `forEach` не ждёт промис, все колбэки стартуют сразу, отказ легко теряется. Цикл — `for...of` или `for`.

Ошибка в середине останавливает хвост, если её не поймали внутри итерации. Уже запущен в этот момент только один `fn`.

---

#### Все сразу

```js
async function mapAll(items, fn) {
  return Promise.all(items.map((item, i) => fn(item, i)));
}
```

`map` синхронно вызывает `fn` для каждого элемента. Все промисы живут до первого `await` внутри `fn`. Время близко к самому медленному, отказ одного отдаёт отказ `all`, остальные не отменяются (п. 85).

Для десяти запросов это нормально. Для десяти тысяч вставок в базу — обвал пула. Браузер на HTTP/1.1 всё равно откроет лишь горсть соединений к одному хосту, остальные будут стоять в очереди сети, а промисы и буферы уже висят в куче.

---

#### Пул на N

В работе не больше `limit` операций. Как только одна закончилась, воркер берёт следующий индекс.

```js
async function mapPool(items, limit, fn) {
  const out = new Array(items.length);
  let next = 0;

  async function worker() {
    while (next < items.length) {
      const i = next++;
      out[i] = await fn(items[i], i);
    }
  }

  const n = Math.min(limit, items.length);
  await Promise.all(Array.from({ length: n }, () => worker()));
  return out;
}
```

`next++` безопасен без атомиков: кусок от чтения `next` до `await` синхронный, второй воркер не вклинится посередине `++` (п. 83: пока стек занят, чужой колбэк не бежит). Гонка появилась бы, если бы индекс увеличивали после `await` и два воркера прочитали одно и то же число до прибавления.

Отказ `fn` отклоняет промис этого воркера, и `Promise.all` тоже отказывает. Упавший воркер из цикла выходит. Живые воркеры об отказе `Promise.all` не узнают: они доделывают текущий элемент и берут следующие индексы, пока список не кончится. Вызывающий уже получил отказ, а хвост ещё выполняется. Чтобы хвост остановить, в `fn` передают `AbortSignal` и абортят его при первом отказе (п. 89).

`limit < 1` при непустом списке в этот код не входит: ноль воркеров даёт `Promise.all([])`, мгновенный успех и ни одного вызова `fn`. Ноль и отрицательное — ошибка аргумента. Рабочий минимум при непустом списке — один воркер.

Пустой `items` — ноль воркеров, успешный пустой массив.

---

#### Ловушка: `await` внутри `map` ничего не сериализует

```js
await Promise.all(
  items.map(async (item) => {
    await step1(item);
    await step2(item); // step2 этого item после своего step1
  }),
);
// step1 разных item идут одновременно
// step2(item) не ждёт step1 чужого item
```

Последовательно то, что связано `await` в одном колбэке. Соседние элементы параллельны, потому что `map` позвал все колбэки сразу. Пул как раз режет эту ширину.

---

#### Сводка

| | Когда стартует следующий | Давление | Время |
|---|---|---|---|
| `for...of` + `await` | после предыдущего | одно | сумма |
| `Promise.all` + `map` | все сразу | размер списка | максимум |
| пул N | не больше N в полёте | N | между суммой и максимумом |

#### TypeScript

Пул обобщают по входу и выходу, чтобы `out` не стал `any[]`.

```ts
async function mapPool<T, R>(
  items: readonly T[],
  limit: number,
  fn: (item: T, index: number) => Promise<R>,
): Promise<R[]> {
  // тело как выше
  return [];
}
```

Типы не ограничивают число одновременных промисов: `limit` — обычное `number`. Компилятор не знает про пул базы. `fn`, который возвращает `R` без промиса, тоже подходит под `Promise<R>` за счёт структурной совместимости только если сигнатура принимает `Promise<R> | R` или `fn` и так `async`. Уже объявленный `Promise<R>` требует промис; лишняя строгость здесь уместна, чтобы в пул не клали синхронный бросок мимо единообразной цепочки. На практике пишут `Promise<R>` и передают `async`-функции.

Что сказать на собеседовании: `await` в `for...of` — очередь, `map` + `all` — все сразу. Пул держит N воркеров и общий индекс. `i++` до `await` не гонка: поток один. Отказ `all` не останавливает уже взятую работу и не останавливает живых воркеров, пока им не передан abort. `forEach(async ...)` не ждёт и теряет отказы.

---

### 89. Cancellation: AbortController, AbortSignal, race-cancel

О чём речь: промис сам по себе нельзя отменить. Можно отклонить ожидание снаружи и попросить операцию остановиться, если она умеет слушать сигнал. `AbortController` как раз эта пара: контроллер абортит, сигнал передают в `fetch`, таймер, свой цикл. На собеседовании отличают «промис, который мы перестали ждать» от «запрос, который правда прервали».

---

#### Контроллер и сигнал

```js
const ctrl = new AbortController();
const { signal } = ctrl;

console.log(signal.aborted); // false
ctrl.abort(); // повторный abort ничего не меняет
console.log(signal.aborted); // true
console.log(signal.reason); // DOMException AbortError, если причину не передали
```

`ctrl.abort(reason)` кладёт в `signal.reason` вашу причину. Без аргумента причина — `DOMException` с именем `AbortError`. `signal.throwIfAborted()` бросает `reason`, если аборт уже был. Подписка: `signal.addEventListener("abort", fn, { once: true })`.

Сигнал передают вниз, не контроллер. Контроллер остаётся у владельца жизненного цикла: кнопки «стоп», размонтирования, таймаута. Дочерние функции только смотрят сигнал и не должны вызывать `abort` чужого сценария, если контракт этого не обещает.

`AbortSignal.timeout(ms)` — сигнал, который абортится сам через мс. `AbortSignal.any([a, b])` — аборт, когда абортился любой из входных. Оба есть в современных браузерах и в актуальном Node; на старом рантайме их может не быть, это проверяют, а не считают вечными.

---

#### Кто реально останавливается

`fetch(url, { signal })` рвёт сеть и отклоняет промис с `AbortError`. Свой цикл обязан смотреть флаг сам:

```js
async function each(items, signal) {
  for (const item of items) {
    signal.throwIfAborted();
    await work(item);
  }
}
```

Проверка между шагами. Уже выполняющийся `work`, если он сигнал не принял, доработает.

Гонка «результат или аборт» только перестаёт ждать. Проигравший промис жив.

```js
function whenAborted(signal) {
  if (signal.aborted) return Promise.reject(signal.reason);
  return new Promise((_, reject) => {
    signal.addEventListener("abort", () => reject(signal.reason), { once: true });
  });
}

async function raceCancel(promise, signal) {
  try {
    return await Promise.race([promise, whenAborted(signal)]);
  } finally {
    // promise всё ещё может завершиться позже. Сеть это не останавливает.
  }
}
```

Имя `raceCancel` честное только если внутри `promise` тот же `signal` уже передан в API, который умеет аборт. Иначе это `race` с отказом по таймауту: ожидание заканчивается, работа нет.

Слушатель на сигнале надо снимать, если промис успел раньше аборта. Иначе замыкание и контроллер держат друг друга дольше нужного. `fetch` это делает сам. В ручной обёртке — `removeEventListener` в `finally` или `{ once: true }` плюс аборт, который точно случится. `{ once: true }` не снимает слушатель, если аборта не было: для одноразового контроллера это терпимо, для долгоживущего сигнала на каждый запрос — утечка. На долгий сигнал слушатель снимают.

---

#### Ловушка: аборт после успеха и «тихий» catch

```js
const ctrl = new AbortController();
const p = fetch("/slow", { signal: ctrl.signal });
ctrl.abort();

try {
  await p;
} catch (e) {
  if (e.name === "AbortError") return; // отмена — не сбой загрузки
  throw e;
}
```

Ловить все ошибки одним пустым `catch` нельзя: сетевой сбой и отмена пользователя — разный исход. Смотрят `e.name === "AbortError"` или сравнивают с `signal.reason`, если передавали свою причину. После `abort(new Error("stopped"))` имя может быть не `AbortError`: ориентир — `signal.reason`, не только строка `"AbortError"`.

Вторая ловушка: `setTimeout`, который абортит контроллер, без `clearTimeout`. Запрос успел, таймер всё ещё висит, потом абортит уже следующий переиспользованный контроллер или просто держит процесс Node. Таймаут и сигнал связывают так, чтобы успех снимал таймер (п. 90).

---

#### TypeScript

`AbortSignal` и `AbortController` приходят из `lib.dom` или из типов Node. Проект только с `lib: ["es2022"]` без DOM и без Node их не видит — это сигнал, что среда в `tsconfig` не та (п. 124).

`fetch` в типах принимает `signal?: AbortSignal | null`. Свой API типизируют так же узко: в параметры сигнал, не контроллер.

```ts
function load(url: string, signal?: AbortSignal): Promise<string> {
  return fetch(url, { signal }).then((r) => r.text());
}
```

Причина аборта в типах — `any` (`signal.reason`). Сужать её самим: своя причина классом или проверкой `name`. Компилятор не доказывает, что операция правда прервётся: тип `signal` не запрещает проигнорировать аргумент.

Что сказать на собеседовании: отменяется не промис, а операция, которая слушает `AbortSignal`. Контроллер у владельца, сигнал — вниз в `fetch` и в циклы. `Promise.race` с отказом по абортe только бросает ожидание. `AbortError` не глотают вместе с настоящими сбоями. Слушатель и таймер снимают, если запрос успел раньше.

---

### 90. Timeouts, retries, backoff, jitter

О чём речь: сеть и чужой сервис иногда молчат или отвечают 503. Таймаут ограничивает ожидание, повтор пробует ещё раз, backoff раздвигает паузы, jitter размазывает их, чтобы все клиенты не ударили в одну секунду. На собеседовании ждут не «завернуть в цикл», а идемпотентность, потолок паузы и отличие таймаута ожидания от остановки работы.

---

#### Таймаут

Короткий вид на современном рантайме: `AbortSignal.timeout(ms)` и API, который сигнал понимает. Промис, который сигнал игнорирует, так не остановить.

Обёртка ожиданием, если сигнала внутри нет:

```js
function withTimeout(promise, ms) {
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error("timeout")), ms);
  });
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}
```

`clearTimeout` в `finally` обязателен. Иначе в Node процесс может не выйти: таймер ещё в очереди. Иначе в браузере таймер позже отклонит уже никому не нужный промис и может всплыть лишним отказом, если гонку собрали неаккуратно.

Медленный `promise` после таймаута всё ещё работает (п. 89). Для `fetch` лучше аборт:

```js
function fetchTimeout(url, ms) {
  const signal = AbortSignal.timeout(ms);
  return fetch(url, { signal });
}
```

Здесь таймер внутри сигнала, отдельный `setTimeout` не висит в пользовательском коде.

---

#### Повтор и пауза

Повторяют то, что можно выполнить дважды с тем же эффектом: GET, PUT с идемпотентным ключом, очередь с дедупом. Слепой повтор POST «списать деньги» без ключа идемпотентности удваивает эффект. Повторяют сеть, таймаут, 408, 429, 500, 502, 503, 504. Не повторяют 400 и 404: сервер уже ответил, что запрос неправильный. 429 уважает `Retry-After`, если он есть, а не только формулу.

Экспонента: пауза `base * 2 ** attempt`, например 100 мс, 200, 400, 800. Сверху потолок `cap`, иначе десятая попытка спит минутами без решения. Снизу тоже есть смысл не ставить ноль: немедленный повтор бьёт в тот же сбой.

Jitter — случайная добавка, чтобы клиенты, упавшие вместе, не проснулись вместе (thundering herd). Полный jitter, практичный по умолчанию: случайное число от 0 до текущей экспоненты (уже с потолком). Equal jitter: половина паузы фиксирована, половина случайна, пауза не схлопывается в ноль. Decorrelated: следующая пауза случайна от `base` до `prev * 3`, тоже с потолком. На собеседовании достаточно экспоненты, потолка и полного jitter; имена остальных — если спросят, чем полный jitter отличается.

```js
function delayMs(attempt, base, cap) {
  const exp = Math.min(cap, base * 2 ** attempt);
  return Math.random() * exp; // full jitter
}

function sleep(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason);
      return;
    }
    const timer = setTimeout(finish, ms);
    function finish() {
      signal?.removeEventListener("abort", onAbort);
      resolve();
    }
    function onAbort() {
      clearTimeout(timer);
      reject(signal.reason);
    }
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}

async function retry(fn, { retries, base, cap, signal }) {
  let last;
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      signal?.throwIfAborted();
      return await fn({ attempt, signal });
    } catch (e) {
      last = e;
      const aborted = signal?.aborted || e?.name === "AbortError";
      if (aborted || attempt === retries) throw e;
      await sleep(delayMs(attempt, base, cap), signal);
    }
  }
  throw last;
}
```

`attempt` от нуля: первая попытка без паузы до неё, пауза — между попытками. `retries: 3` значит одна исходная и три повтора, четыре вызова `fn`. Это проговаривают в API, чтобы «3» не прочитали как «всего три».

Аборт во сне выходит из `sleep` отказом и не начинает следующую попытку. `fn` получает тот же сигнал, чтобы долгий `fetch` тоже прервался, а не только пауза между попытками.

---

#### Ловушка: повтор неидемпотентного и повтор без потолка

```js
for (let i = 0; i < 5; i++) {
  await fetch("/pay", { method: "POST", body }); // каждый заход может списать ещё раз
}
```

Таймаут на первой попытке не значит, что сервер платеж не принял. Повтор безопасен, если клиент шлёт один и тот же `Idempotency-Key`, а сервер по нему отдаёт исходный результат.

Вторая дыра — `base * 2 ** attempt` без `cap` и без jitter. После короткой недоступности все вкладки считают одну и ту же степень двойки и стучатся в одну миллисекунду. Потолок держит худший сон, jitter размазывает стадо.

Третья: бесконечный цикл повтора на 400. Ошибка запроса не лечится ожиданием. Счётчик попыток конечный, классы ошибок разделены до `sleep`.

---

#### Сводка

| Приём | Зачем |
|---|---|
| Таймаут + abort | не ждать вечно и отпустить сеть |
| `clearTimeout` | не держать процесс и не абортить следующий запрос |
| Конечный `retries` | не зациклиться на 400 |
| Экспонента с `cap` | дать сервису подняться, не спать часами |
| Jitter | не синхронизировать клиентов |
| Ключ идемпотентности | повтор POST не дублирует эффект |

#### TypeScript

`retry` обобщают по успешному значению `fn`, чтобы вызывающий не потерял тип ответа.

```ts
async function retry<T>(
  fn: (ctx: { attempt: number; signal?: AbortSignal }) => Promise<T>,
  opts: { retries: number; base: number; cap: number; signal?: AbortSignal },
): Promise<T> {
  return undefined as T;
}
```

Сигнатура не умеет выразить «только идемпотентные вызовы». Это договор в имени функции и в ревью, не в типе. `signal.reason` и пойманный `unknown` в `catch` без `useUnknownInCatchVariables` приходят как `any`; со включённым флагом `catch (e)` — `unknown`, и `e.name` без сужения не читается. Перед `e.name` проверяют `e instanceof Error` или свой класс таймаута. `Error("timeout")` и `AbortError` в типах оба `Error`, различие — рантайм-поле `name` или отдельный класс `TimeoutError`.

Что сказать на собеседовании: таймаут через `AbortSignal` останавливает `fetch`, голый `Promise.race` только перестаёт ждать, таймер снимают в `finally`. Повтор — для идемпотентного и для временных кодов, с конечным числом, потолком паузы и jitter. 400 не ретраят. POST без ключа идемпотентности повторять нельзя: таймаут не доказывает, что эффект не случился.

### 91. Async iterators, `for await…of`

О чём речь: обычный итератор отдаёт следующее значение сразу. Асинхронный отдаёт промис следующего значения: порция ещё не готова, её надо подождать. `for await…of` как раз цикл, который на каждой итерации делает `await`. На собеседовании путают его с `Promise.all` и забывают, что `break` должен закрыть источник, иначе сокет или курсор базы остаётся открытым.

Протокол синхронного итератора — п. 69. Здесь тот же контракт, только `next` возвращает промис.

---

#### Протокол

У объекта есть `Symbol.asyncIterator`. Метод возвращает итератор с `next()`, и этот `next` возвращает `Promise<{ value, done }>`. Когда `done: true`, поток значений кончился.

```js
const cursor = {
  async *[Symbol.asyncIterator]() {
    yield "a";
    await sleep(10);
    yield "b";
  },
};

for await (const row of cursor) {
  console.log(row);
}
// "a", потом через паузу "b"
```

`async function*` — генератор, у которого и `yield`, и `await`. Каждый `yield` становится следующим результатом `next()`. Код между `yield` может ждать I/O.

Потребитель без цикла:

```js
const it = cursor[Symbol.asyncIterator]();
console.log(await it.next()); // { value: "a", done: false }
console.log(await it.next()); // { value: "b", done: false }
console.log(await it.next()); // { value: undefined, done: true }
```

Синхронный итератор в `for await` тоже работает: каждое значение прогоняют через `await`. Удобно для массива. Для массива промисов это ловушка, она ниже.

`for await` по телу последователен. Следующий `next()` не вызывают, пока не кончился `await` тела. Это очередь, не пул (п. 88).

---

#### Закрытие

`break`, `return` и бросок из `for await` зовут `iterator.return()`, если он есть. У `async`-генератора это заходит в `finally`.

```js
async function* lines(signal) {
  try {
    yield "1";
    yield "2";
    yield "3";
  } finally {
    console.log("closed");
  }
}

for await (const line of lines()) {
  console.log(line);
  if (line === "1") break;
}
// "1"
// "closed" — второй и третий yield не выполнятся
```

Свой итератор без генератора обязан реализовать `return` сам: закрыть файл, отменить `fetch`, вернуть соединение в пул. Иначе `break` молча бросает источник открытым. `throw` на итераторе — отдельный канал ошибки в генератор (п. 71); у асинхронного генератора он тоже возвращает промис.

Сигнал отмены (п. 89) в генератор передают аргументом и проверяют перед `yield`. Сам `for await` про `AbortSignal` не знает.

---

#### Ловушка: массив промисов

```js
const jobs = [write("a"), write("b"), write("c")];

for await (const result of jobs) {
  console.log(result);
}
```

`write` вызвался трижды сразу: массив уже заполнен промисами, они уже в работе. `for await` только ждёт их по одному, в порядке индекса, и не ограничивает параллелизм. Отказ второго промиса выйдет на его итерации; третий к этому моменту уже запущен и легко станет необработанным (п. 86).

Параллельный запуск с общим итогом — `Promise.all`. Последовательный старт — `for...of` с `await` внутри, где промис создают на этой итерации, а не заранее. `for await` по массиву промисов не выбирает ни тот, ни другой режим осознанно: старт уже случился при создании массива.

Вторая ловушка — `for await` без `try/finally` у ручного итератора, у которого нет `return`. Выход по `break` не закроет ресурс.

---

#### TypeScript

Типы — `AsyncIterable<T>` и `AsyncIterator<T>`. Генератор — `AsyncGenerator<TYield, TReturn, TNext>`. `for await` требует `AsyncIterable`, синхронный `Iterable` туда тоже допускают типы: компилятор знает про обёртку `await`.

`next(): Promise<IteratorResult<T>>` легко написать руками и забыть `return`. Тип это не ловит: метод опционален. `T` стирается, в рантайме остаётся протокол с `Symbol.asyncIterator`.

Что сказать на собеседовании: `next` асинхронного итератора возвращает промис порции. `for await` ждёт порции по очереди и на `break` вызывает `return`. Массив промисов в `for await` не сериализует старт: промисы уже бегут. Закрытие ресурса — `finally` генератора или свой `return`.

### 92. Streams: WHATWG ReadableStream / TransformStream

О чём речь: поток — последовательность чанков, которую не собирают в одну строку или один `ArrayBuffer`. Потребитель читает по куску, производитель не обязан держать хвост в памяти. В браузере и в современном `fetch` это веб-потоки: `ReadableStream`, `WritableStream`, `TransformStream`. На собеседовании спрашивают, чем поток отличается от `async`-итератора, что такое lock ридера и куда девается backpressure.

Полная тема давления потребителя на производителя — п. 103. Здесь модель трёх типов и как их стыкуют.

---

#### ReadableStream

Поток читают ридером. Пока ридер есть, поток **locked**: второй `getReader()` бросит. После работы ридер отпускают `releaseLock()` или отменяют поток.

```js
const stream = new ReadableStream({
  start(controller) {
    controller.enqueue("a");
    controller.enqueue("b");
    controller.close();
  },
});

const reader = stream.getReader();
console.log(await reader.read()); // { value: "a", done: false }
console.log(await reader.read()); // { value: "b", done: false }
console.log(await reader.read()); // { value: undefined, done: true }
reader.releaseLock();
```

Источник задают объектом: `start` один раз, `pull` когда очереди потребителя нужно ещё, `cancel` когда потребитель отменил. `pull` как раз место, где производитель чувствует спрос: пока внутренний буфер полон, `pull` не зовут.

`ReadableStream.from(asyncIterable)` в современных рантаймах собирает поток из асинхронного итератора (п. 91). Обратно поток сам асинхронно итерируем: `for await (const chunk of stream)` берёт ридер на время цикла. На время цикла поток тоже locked.

`response.body` у `fetch` — `ReadableStream<Uint8Array>` байтов, не строка. `response.text()` вычитывает его целиком. Второй вызов `text()` или `json()` падает: тело уже прочитано, ридер был занят.

---

#### TransformStream и связка

`TransformStream` — пара: во writable пишут, из readable читают уже преобразованное. Между ними `transform(chunk, controller)` и по желанию `flush`.

```js
const upper = new TransformStream({
  transform(chunk, controller) {
    controller.enqueue(String(chunk).toUpperCase());
  },
});

const stream = new ReadableStream({
  start(controller) {
    controller.enqueue("ab");
    controller.close();
  },
});

const out = stream.pipeThrough(upper);
const text = await new Response(out).text();
console.log(text); // "AB"
```

`pipeThrough` стыкует readable с трансформом и возвращает новый readable. `pipeTo(writable)` гонит поток в приёмник до закрытия, отмены или ошибки. Ошибка по дороге отменяет другую сторону: это и есть нормальное завершение связки, в отличие от старого Node `pipe()` (п. 93).

`tee()` делит поток на две ветки. Исходный поток становится locked, оба читателя получают одни и те же чанки. Цена — буфер: медленная ветка заставляет копить чанки для быстрой.

---

#### Ловушка: второй читатель

```js
const reader = stream.getReader();
await stream.getReader(); // TypeError: stream is locked
```

То же делает `for await` по потоку, пока цикл жив, и `response.json()`, которое само берёт ридер. Паттерн «посмотреть первые байты и отдать тот же `response.body` дальше» без `tee()` не работает: первый читатель уже забрал поток.

Отмена — `reader.cancel(reason)` или `stream.cancel`. Источник получает `cancel`. Просто забыть ридер и выйти из функции оставляет поток locked, производитель может висеть в `pull`.

---

#### Сводка

| | Роль |
|---|---|
| `ReadableStream` | источник чанков |
| `WritableStream` | приёмник |
| `TransformStream` | читает одну сторону, пишет другую |
| `pipeThrough` / `pipeTo` | связать до конца или ошибки |
| `tee` | два читателя ценой буфера |

#### TypeScript

Типы живут в DOM lib: `ReadableStream<R>`, `TransformStream<I, O>`. По умолчанию чанк часто `Uint8Array`, потому что сеть и файлы — байты. Свой поток строк — явный аргумент типа `ReadableStream<string>`. Дженерик стирается: в рантайме чанк какой положили в `enqueue`.

`lib` без DOM этих имён не видит. В Node те же глобалы появляются с недавних версий, но имя `ReadableStream` сталкивается с типами пакета `stream`, если в один проект свалены DOM и `@types/node` (п. 93, п. 124).

Что сказать на собеседовании: веб-поток читают одним ридером, второй `getReader` падает, тело `fetch` одноразовое. `pull` зовут, когда потребителю нужно ещё. `TransformStream` плюс `pipeThrough` — преобразование без сборки всего тела в строку. `tee` делится с двумя читателями и может копить буфер.

### 93. Node streams vs Web streams

О чём речь: в Node исторически свои потоки: `Readable`, `Writable`, `Duplex`, `Transform` из модуля `stream`, поверх `EventEmitter`. Веб-потоки — другая модель, её Node тоже умеет. На собеседовании путают `pipe` и `pipeline`, режим `data`/`read` и кто теперь у `fetch` в Node: это уже веб-поток.

---

#### Потоки Node

Читаемый поток Node работает в двух режимах. Пока потребитель сам зовёт `read()`, режим paused. Подписка на `data` переключает в flowing: чанки пушатся событиями, backpressure легко промахнуть, если не слушать `pause`.

```js
const { Readable } = require("stream");

const src = Readable.from(["a", "b"]);
src.on("data", (chunk) => console.log(chunk)); // flowing
src.on("end", () => console.log("end"));
// "a", "b", "end"
```

`async`-итерация по Node-потоку тоже вычитывает его:

```js
for await (const chunk of src) {
  console.log(chunk);
}
```

Ошибка источника — событие `error`, не отказ промиса. Если слушателя `error` нет, Node роняет процесс. `src.pipe(dest)` **не** пробрасывает ошибку в `dest` и не вызывает `destroy` на обоих. Для связки берут `stream.promises.pipeline`: ошибка любого звена уничтожает остальные и возвращается отказом промиса.

```js
const { pipeline } = require("stream/promises");

await pipeline(src, async function* (source) {
  for await (const chunk of source) yield String(chunk).toUpperCase();
}, dest);
```

`pipe()` оставляют только если ошибку и закрытие обрабатывают сами. В новом коде — `pipeline`.

Чанк в Node часто `Buffer`. `Buffer` — подкласс `Uint8Array` в современном Node, но методы `Buffer` (`toString("utf8")`) у голого `Uint8Array` другие. На границе с сетью это всплывает.

---

#### Веб-потоки рядом

`fetch` в Node отдаёт `response.body` как веб-`ReadableStream` байтов, не как `fs.ReadStream`. Код, который делает `body.pipe(fs.createWriteStream(...))`, на этом теле падает: у веб-потока нет метода `pipe` из Node.

Мост из `stream`:

```js
const { Readable } = require("stream");

const nodeReadable = Readable.fromWeb(response.body);
const webReadable = Readable.toWeb(nodeReadable);
```

`fromWeb` / `toWeb` переводят модель «ридер и промис» в модель «события и `read`». Ошибку веб-потока мост превращает в `error` на стороне Node. Дальше её всё равно надо довести до `pipeline`, иначе снова необработанный `error`.

Предпочтение в новом коде на границе HTTP и браузера — веб-потоки (п. 92). Внутри старого кода с `fs` и `zlib` — потоки Node, на краю мост. Два стиля в одной цепочке без моста не стыкуются.

---

#### Ловушка: `pipe` без ошибки

```js
src.pipe(dest);
src.on("error", () => {}); // повесили только на src
// ошибка dest без своего слушателя — падение процесса
// pipe не подписал error с dest на src и не уничтожил пару
```

Вторая ловушка — подписаться на `data` и параллельно звать `read()`, мешая режимы. Один потребитель: либо `data` / `for await`, либо ручной `read()` в paused. И третья: считать `Buffer` и `Uint8Array` взаимозаменяемыми на кодировке. `chunk.toString()` у `Buffer` берёт utf8, у веб-чанка `Uint8Array` метода с кодировкой нет, нужен `TextDecoder`.

---

#### Сводка

| | Node `stream` | Web Streams |
|---|---|---|
| Чтение | `data` / `read()` / `for await` | `getReader` / `for await` |
| Ошибка | событие `error`, без слушателя процесс падает | отказ промиса `read` / `pipeTo` |
| Связка | `pipeline`, не голый `pipe` | `pipeTo` / `pipeThrough` |
| Чанк | часто `Buffer` | часто `Uint8Array` |
| `fetch` в Node | через `Readable.fromWeb` | `response.body` сразу веб-поток |

#### TypeScript

`import { Readable } from "node:stream"` и глобальный `ReadableStream` — разные типы. В проекте с `@types/node` и `lib.dom` имя путается в автоимпорте. Явный импорт из `node:stream` фиксирует сторону Node. `Readable.fromWeb` в типах ждёт веб-`ReadableStream<Uint8Array>`. Дженерик веб-потока на границе с `Buffer` не проверяет кодировку: и там, и там после стирания байты.

Что сказать на собеседовании: у Node свои потоки на событиях, ошибка — событие, голый `pipe` её не протаскивает, для этого `pipeline`. `fetch` в Node отдаёт веб-поток, у него нет `.pipe`, мост — `Readable.fromWeb` / `toWeb`. `Buffer` и `Uint8Array` на `toString` расходятся. Один читатель, один режим: `data` или `read`.

### 94. `queueMicrotask`, `MutationObserver`, `MessageChannel` tricks

О чём речь: иногда нужно «выполнить функцию сразу после текущего стека» или «после отрисовки, но раньше таймера». Отдельного примитива на все случаи долго не было, и очередь микрозадач или задачу собирали побочным API. Сейчас микрозадачу ставят `queueMicrotask`. `MutationObserver` и `MessageChannel` остаются на собеседовании как история полифилов и как способ выбрать очередь: микрозадачу или задачу (п. 83).

---

#### `queueMicrotask`

`queueMicrotask(fn)` ставит `fn` в очередь микрозадач. Она бежит, когда стек опустеет, раньше таймера и раньше paint.

```js
console.log("a");
queueMicrotask(() => console.log("micro"));
setTimeout(() => console.log("task"), 0);
console.log("b");
// a, b, micro, task
```

`Promise.resolve().then(fn)` по очереди то же самое, но создаёт промис. Если `fn` бросит, у `then` это отказ промиса: без `.catch` он становится необработанным rejection (п. 86). Бросок из колбэка `queueMicrotask` — обычное необработанное исключение задачи микроочереди, не отказ промиса. Для «просто отложить до конца стека» берут `queueMicrotask`, промис не заводят.

Рекурсивный `queueMicrotask` не отдаёт цикл задачам и отрисовке (п. 83, п. 99).

---

#### `MutationObserver` как микрозадача

Колбэк `MutationObserver` в браузере доставляют микрозадачей: после текущего стека, пачкой накопившихся записей. До появления `queueMicrotask` микрозадачу имитировали так: создать текстовый узел, наблюдать его, поменять `data`.

```js
function oldMicrotask(fn) {
  const el = document.createTextNode("");
  const obs = new MutationObserver(() => {
    obs.disconnect();
    fn();
  });
  obs.observe(el, { characterData: true });
  el.data = "x";
}
```

В новом коде так не пишут: есть `queueMicrotask`, трюк зависит от DOM и от того, что браузер не схлопнет уведомление. На собеседовании достаточно знать, что колбэк наблюдателя — микрозадача, поэтому он обгоняет `setTimeout(0)`, и что полифил устарел. Сам наблюдатель по назначению — реакцией на дерево, не планировщиком.

---

#### `MessageChannel` как задача

`port.postMessage` доставляет сообщение **задачей**, не микрозадачей. Канал без сети и без таймера: два порта в одном окне. Так исторически делали аналог `setImmediate`: уступить цикл, чтобы браузер успел paint, и не платить задержку таймера в 4 мс (п. 82).

```js
const channel = new MessageChannel();

function yieldTask(fn) {
  channel.port1.onmessage = () => fn();
  channel.port2.postMessage(null);
}

queueMicrotask(() => console.log("micro"));
yieldTask(() => console.log("task"));
setTimeout(() => console.log("timeout"), 0);
// micro, потом task, потом timeout
// task и timeout оба задачи; порядок между своими источниками не путать с «всегда раньше таймера»
```

Сообщение канала и таймер — разные источники задач. «Раньше `setTimeout(0)`» на практике часто правда, спека не обещает один общий FIFO на все источники (п. 82). Обещание другое: это не микрозадача, отрисовка между такими задачами возможна. Микрозадача отрисовку не пропускает.

В Node `MessageChannel` тоже есть (глобал с недавних версий). Для «после I/O, до таймеров» там штатно `setImmediate` (п. 82), канал не нужен.

---

#### Ловушка: микрозадача вместо уступки

Планировщик, который дробит длинную работу через `queueMicrotask` или через `MutationObserver`, цикл не отпускает: следующая микрозадача встаёт в ту же очередь, paint не наступает. Уступка кадру — задача: `MessageChannel`, `setTimeout` или `scheduler.yield` (п. 105).

Вторая ловушка — оставить `port1.onmessage` навсегда и постить в общий канал из нескольких мест. Один обработчик перезаписывают, чужой колбэк пропадает. На каждый заход свой канал или одна очередь колбэков поверх одного порта.

---

#### TypeScript

`queueMicrotask(fn: () => void): void` есть и в DOM, и в типах Node. `MutationObserver` — только DOM: в Node-проекте без DOM его быть не должно. `MessageChannel` есть в обоих, но типы портов и `postMessage` расходятся деталями lib. Среда задаётся `lib` / типами Node (п. 124), не кастом на каждый вызов.

Компилятор не отличает микрозадачу от задачи. Аннотация `() => void` одна и та же у `queueMicrotask`, таймера и `onmessage`.

Что сказать на собеседовании: `queueMicrotask` — прямая микрозадача, бросок из неё не промис-rejection. `MutationObserver` тоже микрозадача, как планировщик это старый полифил. `MessageChannel` ставит задачу и может пропустить paint, в отличие от цепочки микрозадач. Рекурсия микрозадач цикл голодает.

---

### 95. `requestAnimationFrame`, `requestIdleCallback`

О чём речь: таймер меряет миллисекунды. Кадр и простой меряет браузер. `requestAnimationFrame` ставит колбэк перед следующей отрисовкой. `requestIdleCallback` — когда браузер считает, что есть свободное время до дедлайна кадра. На собеседовании их путают с `setTimeout(16)` и кладут тяжёлую работу не в ту очередь.

Оба есть только в окне с отрисовкой. В Node и в воркере без окна их нет.

---

#### Кадр

`requestAnimationFrame(cb)` возвращает id, снять — `cancelAnimationFrame(id)`. Колбэк получает `DOMHighResTimeStamp`: время кадра, одно и то же у всех колбэков этого кадра. Браузер вызывает их перед style/layout/paint, пачкой, в порядке постановки.

```js
const id = requestAnimationFrame((ts) => {
  console.log(ts); // время кадра, не «сейчас плюс 16»
  element.style.transform = "translateX(10px)";
});
cancelAnimationFrame(id);
```

Вложенный вызов из колбэка планирует **следующий** кадр, не второй заход в этом же. Цикл анимации — снова `requestAnimationFrame` в конце колбэка.

Фоновая вкладка колбэки останавливает или сильно режет. Это не баг: кадр всё равно никто не видит. `setTimeout` в фоне тоже зажимают, но он не привязан к vsync и легко промахивается мимо кадра, отсюда дёрганье, если анимацию ведут таймером.

16 мс — оценка для 60 Гц, не контракт. Экран 120 Гц зовёт колбэк чаще. Опоздавший колбэк не «дорисовывает пропущенные», следующий придёт уже с новым `ts`. Шаг анимации считают разницей времён, не константой 16.

В колбэке меняют то, что влияет на картинку. Тяжёлый расчёт без визуала съедает бюджет кадра и даёт jank: layout не успеет к paint.

---

#### Простой

`requestIdleCallback(cb, { timeout })` зовут, когда у браузера есть окно до следующего кадра. `deadline.timeRemaining()` — сколько миллисекунд ещё можно занять, верх около 50 мс, и значение может быть нулём. `deadline.didTimeout` истинно, если сработал `timeout` и браузер отдал колбэк, даже когда простоя нет.

```js
requestIdleCallback(
  (deadline) => {
    while (deadline.timeRemaining() > 0 && queue.length > 0) {
      process(queue.shift());
    }
    if (queue.length > 0) requestIdleCallback(run);
  },
  { timeout: 1000 },
);
```

Без `timeout` колбэк могут не вызвать очень долго: вкладка занята анимацией. С `timeout` его вызовут к сроку, но `timeRemaining()` тогда может быть нулевым: это запасной ход, не свободные 50 мс.

Сюда кладут отложенную работу: телеметрия, прогрев кэша, разбор несрочного результата. Не кладут анимацию и не кладут запись в DOM, которая синхронно устраивает layout посреди чужого кадра.

Safari долго не имел `requestIdleCallback`. Полагаться на него без проверки `typeof` или запасного `setTimeout` на старых движках нельзя. Это не полифил семантики: таймер не знает про `timeRemaining`.

---

#### Ловушка: цикл кадра без отмены

```js
function loop() {
  requestAnimationFrame(() => {
    tick();
    loop();
  });
}
loop();
```

После ухода со страницы или размонтирования колбэк продолжит планировать себя, пока вкладка жива. Id хранят и снимают `cancelAnimationFrame`. То же с `cancelIdleCallback`.

Вторая ловушка — ждать от `requestAnimationFrame` микрозадачу или «сразу после стека». Это слот кадра, его обгоняют и синхронный код, и микрозадачи текущего хода. Третья — считать `setTimeout(fn, 0)` и кадр эквивалентными: таймер может попасть в середину кадра и спровоцировать лишний layout.

---

#### Сводка

| | Когда | Для чего | Чем снимают |
|---|---|---|---|
| `requestAnimationFrame` | перед paint следующего кадра | визуальное обновление | `cancelAnimationFrame` |
| `requestIdleCallback` | простой или `timeout` | несрочная работа | `cancelIdleCallback` |
| `setTimeout` | таймер, не vsync | отложенная задача | `clearTimeout` |

#### TypeScript

Оба API — DOM lib, возврат id — `number`. В типах Node их нет: вызов в серверном файле — сигнал, что в `tsconfig` подтянут DOM не туда, или что код случайно общий у клиента и сервера. `IdleDeadline` описывает `timeRemaining(): number` и `didTimeout: boolean`. Типы не гарантируют, что колбэк вообще вызовут: `timeout` в опциях опционален, отсутствие простоя — рантайм.

Что сказать на собеседовании: `requestAnimationFrame` — один слот перед отрисовкой, время кадра общее, шаг считают по разнице `ts`, в фоне его душат. Вложенный вызов — следующий кадр. `requestIdleCallback` — остаток бюджета, без `timeout` могут не позвать, для анимации не используют. Оба id надо отменять. `setTimeout(16)` к vsync не привязан.

### 96. Web Workers, SharedWorker, Service Worker (JS-модель)

О чём речь: воркер — другой агент. У него свой стек, свой event loop и своя куча (п. 81). Общих `let` с окном нет. Обмен — сообщениями (п. 97), не замыканием. Три вида отличаются тем, кто их держит и сколько страниц с ними говорит. На собеседовании смешивают «фоновый поток страницы», «один на все вкладки» и «прокси сети, который переживает документ».

---

#### Dedicated Worker

`new Worker(url)` создаёт поток, привязанный к одному владельцу. Скрипт воркера не видит `document`, `window` и DOM. Видит `self`, `fetch`, таймеры, свой цикл событий.

```js
const worker = new Worker(new URL("./work.js", import.meta.url));
worker.postMessage({ n: 2 });
worker.onmessage = (e) => console.log(e.data); // ответ от воркера
worker.onerror = (e) => console.log(e.message);
```

```js
// work.js
self.onmessage = (e) => {
  self.postMessage(e.data.n * 2);
};
```

Классический воркер грузит скрипт как classic script: свои `import` ESM не работают, чужие файлы подключают `importScripts`. Модульный — `new Worker(url, { type: "module" })`: обычный `import`, `importScripts` нет. URL воркера режется same-origin правилами; чужой скрипт без CORS не стартует.

`worker.terminate()` убивает агента сразу, `finally` внутри воркера не обещают. Из воркера наружу — `self.close()`.

Тяжёлый расчёт уносят сюда, чтобы не занимать стек окна. Пока воркер считает, страница рисуется. Сообщение придёт задачей в цикл окна, не синхронным `return`.

---

#### SharedWorker

Один агент на несколько контекстов одного источника: несколько вкладок. Снаружи — `new SharedWorker(url)` и порт `worker.port`. Внутри воркер слушает `onconnect` и забирает `e.ports[0]`.

```js
const shared = new SharedWorker("shared.js");
shared.port.start();
shared.port.postMessage("hi");
shared.port.onmessage = (e) => console.log(e.data);
```

```js
// shared.js
const ports = [];
self.onconnect = (e) => {
  const port = e.ports[0];
  ports.push(port);
  port.onmessage = (ev) => {
    for (const p of ports) p.postMessage(ev.data);
  };
};
```

`port.start()` нужен, если сообщения читают через `onmessage`: пока порт не стартовал, они копятся. У dedicated worker порт снаружи скрыт, `start` делает сам `Worker`.

Жизнь привязана к браузеру и к тому, есть ли ещё порты, не к одной вкладке. Закрытие одной вкладки агента не убивает, пока есть другие клиенты. Это не service worker: сеть он сам не перехватывает.

---

#### Service Worker

Регистрация из страницы: `navigator.serviceWorker.register("/sw.js")`. Скрипт ставится, потом активируется, потом получает события `fetch`, `message`, пуши. У него нет DOM. Он может пережить закрытие вкладки: это не «поток на время `new Worker`», а отдельная установка в браузере со своим циклом.

Упрощённая модель скрипта:

```js
self.addEventListener("install", (event) => {
  event.waitUntil(caches.open("v1")); // активироваться после готовности кэша
});

self.addEventListener("activate", (event) => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener("fetch", (event) => {
  event.respondWith(fetch(event.request));
});
```

`install` — постановка новой версии. `activate` — старая версия отпустила клиентов. `fetch` — браузер спрашивает воркер, чем ответить на запрос страницы в области действия. `waitUntil` продлевает событие, пока промис не завершится: без этого процесс могут усыпить до конца асинхронной работы.

Новая версия не вытесняет старую, пока открытые клиенты держат прежнюю. `skipWaiting()` в `install` просит активироваться сразу. Это JS-модель жизненного цикла, не рецепт кэша.

Service worker не делит кучу со страницей. Данные — снова сообщения или Cache / IndexedDB, не общая переменная.

---

#### Ловушка: ждать общий `let`

```js
let n = 1;
const worker = new Worker("work.js");
worker.postMessage("go");
// work.js не видит n и не может сделать n = 2
// наружу придёт копия в сообщении, не ссылка на n
```

Функцию в воркер тоже не передать: замыкание не клонируется (п. 97). Воркер — отдельный файл или модуль со своим кодом.

Вторая ловушка — считать service worker «воркером вкладки». `terminate` у dedicated убивает поток сейчас. Service worker после `register` живёт по правилам install/activate, закрытие документа его не обязано остановить, а `fetch` может прийти, когда страницы уже нет. Третья: забыть `{ type: "module" }` и писать `import` в classic-воркере — скрипт не стартует.

---

#### Сводка

| | Кто держит | Сколько клиентов | DOM | Типичные события |
|---|---|---|---|---|
| Dedicated | одна страница | один | нет | `message` |
| Shared | браузер, пока есть порты | много вкладок | нет | `connect`, сообщение порта |
| Service | установка браузера | клиенты в scope | нет | `install`, `activate`, `fetch` |

#### TypeScript

Типы окна и типы воркера конфликтуют: в окне есть `document`, в воркере — `DedicatedWorkerGlobalScope` и нет DOM. Один `tsconfig` с `lib: ["dom", "webworker"]` смешивает глобалы. Файл воркера проверяют отдельным проектом с `lib: ["webworker"]` или тройной директивой, не общим DOM-набором страницы (п. 117, п. 124).

`new Worker(url, { type: "module" })` типы принимают. Они не проверяют, что файл по URL действительно модуль. `postMessage` по умолчанию структурно клонирует `any`; дженерик воркера в lib узкий контракт сообщений сам не выводит, его задают обёрткой.

Что сказать на собеседовании: у воркера свой цикл и своя куча, общих переменных со страницей нет. Dedicated — один владелец, Shared — порт на несколько вкладок, Service — install/activate/fetch и жизнь отдельно от документа. Classic и module — разные способы загрузить скрипт. `terminate` не равен закрытию вкладки у service worker.

### 97. `postMessage`, structured clone, transferable

О чём речь: сообщение в воркер, в другое окно или через `MessagePort` не передаёт ссылку на объект. Движок копирует данные алгоритмом structured clone либо переносит отдельные объекты так, что у отправителя их больше нет. На собеседовании ждут, почему функция и экземпляр класса не доезжают, и чем transfer отличается от копии `ArrayBuffer`.

Тот же алгоритм копирования, что у `structuredClone` (п. 54). `postMessage` добавляет список transfer.

---

#### Что копируется

Клонируются обычные объекты, массивы, даты, `Map`/`Set`, `ArrayBuffer` (если не в списке transfer), `Blob`, типизированные массивы, циклы ссылок внутри одного сообщения. Копия независима: мутация у получателя отправителя не меняет.

Не клонируются функции, DOM-узлы, символы как ключи свойств (ключ пропадает или бросает, в зависимости от объекта), слабые коллекции как носители смысла. Геттер при клонировании вызывают и копируют уже значение. Прототип получателя — `Object.prototype` или ближайший стандартный прототип (`Array`, `Map`), не ваш класс.

```js
class User {
  constructor(name) {
    this.name = name;
  }
  hello() {
    return this.name;
  }
}

worker.postMessage(new User("Ada"));
// у получателя { name: "Ada" }
// hello нет, instanceof User ложь: класса в том агенте может не быть вообще
```

```js
worker.postMessage({ fn() {} }); // DataCloneError
```

Ошибка клонирования синхронная: `postMessage` бросает в отправителе, сообщение не встаёт в очередь.

---

#### Transferable

Второй аргумент — список объектов, владение которыми переезжает. Типичные: `ArrayBuffer`, `MessagePort`, `ReadableStream`, `ImageBitmap`, `OffscreenCanvas`. Буфер у отправителя становится непригодным: `byteLength === 0`, любое чтение представления бросает.

```js
const buffer = new Uint8Array([1, 2, 3]).buffer;

worker.postMessage(buffer, [buffer]);
console.log(buffer.byteLength); // 0, память отдана
```

Это не копия. Большой файл в воркер и обратно имеет смысл переносить, а не клонировать дважды. Перенести можно только то, что спека считает transferable. Обычный объект во второй аргумент класть нельзя.

Один буфер нельзя и прочитать в клоне сообщения, и перенести: если он достижим из данных и указан в списке, он переносится, в клоне у получателя живой буфер, у отправителя — пустой.

`SharedArrayBuffer` в список transfer как копию не кладут. Его можно передать в сообщении только когда агенты имеют право на общую память (п. 98): получатель видит ту же память, не снимок.

---

#### Ловушка: пользоваться буфером после transfer

```js
const view = new Uint8Array(buffer);
worker.postMessage(buffer, [buffer]);
view[0] = 1; // TypeError: буфер отсоединён
```

Вторая ловушка — большой объект без transfer. Сообщение молча копирует мегабайты, страница дёргается на клонировании, хотя «мы же просто послали». Третья: ждать, что получатель вызовет метод класса. В сообщение кладут данные, поведение на той стороне написано своим кодом.

`postMessage` в окно (`window.opener`, iframe) дополнительно фильтрует origin вторым/третьим аргументом `targetOrigin`. В воркер origin так не передают: канал и так приватный. Перепутать сигнатуры «данные, origin» и «данные, transfer» — классика: строка `"*"` не список буферов, список случайно уедет не туда или бросит.

---

#### TypeScript

`postMessage(message: any, transfer: Transferable[]): void` на `Worker` не связывает тип `message` с тем, что реально клонируется. Функция в объекте типах может быть разрешена, если её зашили в интерфейс, а в рантайме будет `DataCloneError`. Узкий тип сообщения — свой дженерик-обёртка, не дефолт lib.

`ArrayBuffer` после transfer в типах остаётся `ArrayBuffer`. Отсоединённость — рантайм. `structuredClone<T>(value: T): T` тоже врёт про класс: тип обещает `User`, в рантайме простой объект (п. 54).

Что сказать на собеседовании: `postMessage` клонирует structured clone, не ссылку. Функции и методы класса не переносятся, прототип теряется. Transfer отдает владение `ArrayBuffer` и портом, у отправителя буфер пустой. Общая память — это `SharedArrayBuffer`, не transfer копии. Ошибка клона синхронная.

---

### 98. SharedArrayBuffer, Atomics, memory model

О чём речь: обычное сообщение копирует данные. `SharedArrayBuffer` — один кусок памяти, который видят несколько агентов. Писать туда без синхронизации — гонка. `Atomics` даёт операции, которые не рвутся посередине, и ожидание с пробуждением. На собеседовании это единственная настоящая общая память в JS и причина, почему `Atomics.wait` нельзя звать на главном потоке.

Нужна изоляция источника: заголовки COOP/COEP (cross-origin isolated). Без них `SharedArrayBuffer` в браузере может быть спрятан или `new SharedArrayBuffer` бросит. Это последствие Spectre: точный таймер и общая память вместе читают чужой процесс. В Node изоляция страницы не нужна, буфер доступен.

---

#### Общая память

```js
const sab = new SharedArrayBuffer(4);
const view = new Int32Array(sab);

view[0] = 1;
worker.postMessage(sab);
// получатель видит тот же байтовый кусок, не копию
// view[0] = 2 у воркера меняет view[0] у отправителя
```

Обычный массив и обычный объект так не шарят. Даже `ArrayBuffer` без share при `postMessage` копируется, а при transfer уезжает целиком и у отправителя отбирается (п. 97).

Типизированный вид (`Int32Array` и соседи) — способ читать ячейки. Два агента могут держать свои view на один буфер.

---

#### Atomics

Запись `view[0] = 1` не атомарна с точки зрения модели: сосед может прочитать рваное или устаревшее значение, и оптимизатор имеет право не увидеть чужую запись. Для ячеек, с которыми работают `Atomics`, используют его операции.

```js
const sab = new SharedArrayBuffer(4);
const view = new Int32Array(sab);

Atomics.store(view, 0, 1);
console.log(Atomics.load(view, 0)); // 1
console.log(Atomics.add(view, 0, 5)); // 1, прежнее значение
console.log(Atomics.load(view, 0)); // 6

const prev = Atomics.compareExchange(view, 0, 6, 9);
// если в ячейке было 6, стало 9; prev — что было
```

`add`, `sub`, `and`, `or`, `xor`, `exchange`, `compareExchange` делают чтение-изменение-запись одной операцией. `wait` засыпает агента, пока ячейка не сменится или не придёт `notify`:

```js
// в воркере
Atomics.wait(view, 0, 0); // спать, пока view[0] === 0
// на главном, когда данные готовы
Atomics.store(view, 0, 1);
Atomics.notify(view, 0, 1);
```

`wait` **блокирует поток агента**. В браузере на главном потоке он бросает `TypeError`: иначе вкладка замерла бы без event loop. В воркере блокируется только этот воркер. Пока он спит в `wait`, его очередь сообщений не разбирается. `notify` должен прийти из другого агента.

Модель памяти: атомарные операции по ячейке упорядочены (последовательно согласованы друг с другом). Неатомарный доступ к той же ячейке рядом с `Atomics` программу не защищает. Ждать «байт сам подхватится из `view[i] =`» нельзя.

`Atomics.waitAsync` не блокирует: возвращает промис или сразу `{ async: false }`, если ждать не нужно. Им можно пользоваться там, где `wait` запрещён, но это уже ожидание через цикл событий, не спящий поток.

---

#### Ловушка: `wait` на главном и потерянный `notify`

```js
Atomics.wait(view, 0, 0); // TypeError в окне браузера
```

В Node на главном потоке `wait` разрешён и блокирует весь цикл: таймеры, I/O и то самое сообщение, которое должно сделать `notify`, не выполнятся. Получается зависание (п. 99).

Вторая ловушка — `notify` раньше `wait`. Если воркер ещё не уснул, уведомление никого не будит, потом `wait` видит старое ожидаемое значение и спит вечно. Перед сном значение проверяют в цикле: `wait` как раз возвращается сразу, если ячейка уже не равна ожидаемой. Гонка «notify ушёл в пустоту» лечится записью состояния в ячейку до `notify` и проверкой её в условии `wait`, а не отдельным «сначала постучи, потом поспи» без значения.

Третья: общая память без изоляции в браузере. Код с `new SharedArrayBuffer` падает не из-за синтаксиса, а из-за заголовков документа.

---

#### TypeScript

`SharedArrayBuffer` и `Atomics` приходят из lib ES2020/ES2024, не из типов «воркер или нет». `Atomics.store(typedArray, index, value)` требует целочисленный typed array. `SharedArrayBuffer` не назначается в `ArrayBuffer` во всех сигнатурах: `postMessage` и API, которые забирают буфер, часто разделены специально, чтобы случайно не отдать общую память туда, где ждут копию.

Типы не знают про COOP/COEP и не запрещают `Atomics.wait` на главном потоке: и окно, и воркер в типах могут видеть одну и ту же функцию. Ограничение — рантайм.

Что сказать на собеседовании: `SharedArrayBuffer` — одна память на несколько агентов, в браузере нужна изоляция. Писать ячейки через `Atomics`, голый `view[i] =` рядом — гонка. `wait` блокирует агента и на главном потоке браузера запрещён. `notify` без записи нового значения можно проспать. Это не structured clone.

### 99. Deadlocks/starvation на уровне event loop

О чём речь: у одного агента нет двух потоков, которые ждут друг друга на мьютексе ОС. Зависание всё равно бывает двух видов. Голодание: очередь микрозадач или `nextTick` никогда не пустеет, и таймер, I/O, paint не получают стек. Взаимное ожидание: промис или `Atomics.wait` ждёт того, кто может проснуться только на этом же занятом стеке. На собеседовании это продолжение п. 83, уже как поломка системы, а не как порядок логов.

---

#### Голодание

Микрозадачи вычерпывают до конца. Пока колбэк ставит следующую микрозадачу, цикл до задач не доходит.

```js
function spin() {
  queueMicrotask(spin);
}
spin();
setTimeout(() => console.log("timer"), 0);
// "timer" не печатается
```

В Node то же делает рекурсивный `process.nextTick`: фазы libuv не наступают, I/O стоит (п. 82). Симптом — «таймер на ноль не стреляет» и мёртвый ввод в браузере. Лечение: шаг, который можно отложить, ставить задачей (`setTimeout`, `setImmediate`, `MessageChannel`, п. 94) или уступать через `scheduler.yield` (п. 105). Микрозадачей оставляют короткий хвост текущего хода.

Долгий синхронный кадр — та же картина снаружи: очереди полны, стек не пустеет. Это не взаимная блокировка, это один кадр, который не возвращается (п. 81).

---

#### Взаимное ожидание на одном цикле

Лок на промисах легко берёт сам себя через `await`. Второй захват ждёт `unlock`, а `unlock` стоит после `await`, который ждёт второй захват.

```js
let held = false;
const waiters = [];

function lock() {
  if (!held) {
    held = true;
    return Promise.resolve();
  }
  return new Promise((resolve) => waiters.push(resolve));
}

function unlock() {
  const next = waiters.shift();
  if (next) next();
  else held = false;
}

async function outer() {
  await lock();
  await inner();
  unlock();
}

async function inner() {
  await lock(); // ждёт unlock, который сделает только outer после inner
  unlock();
}

outer(); // зависло
```

Оба кадра уже отдали стек на `await`, цикл свободен, но разблокировать некому: единственный `unlock` стоит в `outer` после строки, которая ждёт `inner`. Это взаимное ожидание без второго потока.

Тот же рисунок у пула с одним слотом (п. 88): задача держит слот и `await`-ит другую задачу, которой нужен тот же слот.

`Atomics.wait` на главном потоке Node блокирует цикл целиком. Если разбудить его может только `notify` из колбэка I/O или таймера, колбэк не выполнится, пока `wait` не вернётся. В браузере на главном такой `wait` просто бросает (п. 98). В воркере `wait` блокирует только воркер: если воркер ждёт сообщение с главного, а главный ждёт `postMessage` от этого воркера, пара тоже стоит. Пока агент спит в `wait`, его `onmessage` не бежит.

---

#### Ловушка: «цикл же свободен»

После `await` стек пуст, таймеры идут, страница живая, а экран операции крутится вечно. Это не голодание микрозадачами. Смотреть, кто должен вызвать `resolve` / `unlock` / `notify` и не стоит ли этот вызов за тем же ожиданием.

Вторая картина — голый `while` без `await` «пока флаг не сменят». Флаг меняет только колбэк, колбэк не войдёт, пока `while` не кончится. Флаг так не дождаться. Ожидание флага — промис, который резолвит колбэк, или `Atomics.wait` в воркере, не пустой цикл на главном потоке.

---

#### Сводка

| | Стек | Кто не дождётся | Как выглядит |
|---|---|---|---|
| Голодание микрозадачами | пустой между микрозадачами | таймеры, I/O, paint | вечный `queueMicrotask` / `nextTick` |
| Длинный синхронный кадр | занят | всё остальное | цикл без `await` |
| Лок через свой `await` | пуст | `unlock` после вложенного захвата | операция висит, страница жива |
| `Atomics.wait` на том же агенте, который должен `notify` | заблокирован | сообщение и таймер этого агента | процесс Node молчит |

#### TypeScript

Типы промисов не видят цикл ожидания. `Promise<void>` у `lock` и у `inner` компилятор устраивает, зависание — рантайм. `Atomics.wait` в типах возвращает ` "ok" | "timed-out" | "not-equal" ` и не говорит, что вызов блокирует агент. Линтер на плавающие промисы (п. 86) эту взаимную блокировку не находит: промисы как раз ждут, они не брошены.

Что сказать на собеседовании: голодание — микрозадачи или `nextTick` не отдают цикл задачам. Взаимное ожидание на одном агенте — лок, который ждут изнутри удержания, или `wait`, который не даёт выполниться своему `notify`. Пустой `while` флага не дождётся: колбэк не войдёт в занятый стек. Страница может оставаться отзывчивой и всё равно не закончить операцию.

### 100. Top-level await, module evaluation order

О чём речь: `await` можно писать в теле ES-модуля, не оборачивая в `async function`. Оценка модуля тогда сама возвращает промис, и все, кто его импортирует, ждут этот промис. На собеседовании спрашивают, почему один медленный модуль тормозит старт, почему цикл импортов с верхним `await` встаёт навсегда и почему `require` такого файла не умеет.

Модули и живые привязки — п. 106. Здесь только пауза оценки.

---

#### Порядок без верхнего await

Граф сначала связывают: у модулей есть записи экспорта, тела ещё не выполнены, импорт в TDZ, пока оценка не дойдёт до инициализации (п. 32, п. 40). Потом тела выполняют в глубину: зависимости раньше импортёра. Побочный эффект модуля случается один раз.

Верхний `await` разрешён только в ES-модуле. В classic script и в CommonJS это синтаксическая ошибка.

```js
// config.mjs
const res = await fetch("/config.json");
export const config = await res.json();
```

```js
// main.mjs
import { config } from "./config.mjs";
console.log(config.host); // импорт уже дождался fetch
```

Пока `config.mjs` висит на `fetch`, его оценка не закончена. `main.mjs` не начинает тело: импортёр ждёт промис зависимости. Соседний модуль, который от `config.mjs` не зависит, может оцениваться параллельно с этим ожиданием. Зависимая цепочка — нет.

Динамический `import("./config.mjs")` возвращает промис, который резолвится уже после верхних `await` этого модуля. Статический импорт того же файла в другом модуле делит одну оценку: второй раз `fetch` не пойдёт.

---

#### Цикл

Обычный цикл ESM без `await` жив за счёт живых привязок: тело A может увидеть экспорт B, если к моменту чтения B уже инициализировал привязку. Верхний `await` в цикле легко требует, чтобы сосед **закончил** оценку, а сосед ждёт того же от вас.

```js
// a.mjs
import { b } from "./b.mjs";
export const a = 1;
await null;
console.log(b);

// b.mjs
import { a } from "./a.mjs";
export const b = 2;
await null;
console.log(a);
```

Каждый модуль дошёл до `await` и ждёт завершения другого, потому что импортированная привязка нужна после паузы, а завершение соседа зависит от завершения первого. Оценка графа не заканчивается. Без `await` тот же цикл мог напечатать значения, если читать их после инициализации, а не ждать конца модуля.

Практическое правило: верхний `await` в модуле, который участвует в цикле, не ставят. Циклы вообще режут (п. 106), с `await` они превращаются в зависание старта, не в TDZ на одну строку.

---

#### Ловушка: общий модуль с сетью

```js
// db.mjs — импортируют и страница, и тесты, и CLI
export const db = await connect(process.env.DATABASE_URL);
```

Любой импортёр `db.mjs` ждёт сеть до первой строки своего тела. Ошибка соединения отклоняет оценку модуля: падает не один вызов, а загрузка всего графа, который на нём сидит. Повторный импорт не «попробует ещё раз»: оценка модуля одна, отказ запоминается.

Тяжёлый и падающий I/O на верхнем уровне широкого модуля задерживает и роняет всех. Ленивый старт — функция `getDb()`, которую вызывают по месту, или динамический `import()` из того кода, которому соединение правда нужно.

`require()` модуля с верхним `await` в Node не работает: CommonJS синхронный, ждать нечем, будет ошибка вида `ERR_REQUIRE_ASYNC_MODULE`. Такой файл грузят только `import` / `import()`.

---

#### TypeScript

Верхний `await` — синтаксис модуля. При `"module": "commonjs"` компилятор его не примет как есть: в CJS нет честной паузы оценки. Нужен `module` уровня `es2022`, `esnext`, `nodenext` или `preserve`, и файл как модуль (`import`/`export` или `"type": "module"`). Понижение target само по себе верхний `await` в рабочий `require` не превращает.

Типы экспорта после `await` обычные: `config` имеет тип JSON-разбора, какой вы аннотировали. Компилятор не знает, что импортёр блокируется на сети. `Awaited` тут ни при чём: пауза в рантайме графа, не в типе выражения.

Что сказать на собеседовании: верхний `await` делает оценку модуля промисом, статические импортёры ждут его. Зависимости идут раньше тела. Независимые ветки графа могут идти вместе с ожиданием, цепочка импортёров — нет. Цикл с верхним `await` зависает. Широкий модуль с сетью наверху тормозит всех и не ретраится вторым импортом. `require` такого модуля не грузит.

---

### 101. Async context: `AsyncLocalStorage`, `AsyncContext` proposal

О чём речь: у запроса есть свой id, свой пользователь, свой логгер. Прокидывать их аргументом через каждый `await` и каждый колбэк тяжело, а глобальная переменная врёт, как только два запроса идут вместе. Асинхронный контекст — ячейка, которая едет вместе с продолжениями текущего захода и не видна соседнему запросу. В Node это `AsyncLocalStorage`. В языке на ту же роль рассчитано предложение `AsyncContext`, оно не заменяет ALS во всех движках.

---

#### `AsyncLocalStorage`

Класс из `node:async_hooks`. `run(store, fn)` выполняет `fn` и все асинхронные операции, которые родились внутри этого вызова, с данным хранилищем. `getStore()` возвращает его или `undefined`, если текущий ход снаружи `run`.

```js
const { AsyncLocalStorage } = require("node:async_hooks");

const als = new AsyncLocalStorage();

function log(msg) {
  const store = als.getStore();
  console.log(store?.requestId, msg);
}

als.run({ requestId: "r1" }, () => {
  log("start"); // "r1 start"
  setTimeout(() => log("timer"), 0); // "r1 timer"
});

setTimeout(() => log("outside"), 0); // "undefined outside"
```

Таймер, промис, `nextTick` и I/O, запланированные внутри `run`, видят то же хранилище после `await`. Второй `run` рядом кладёт другое хранилище. Один агент обслуживает оба запроса по очереди, ячейки не смешиваются, потому что продолжение помнит ресурс, в котором его создали, а не «последний глобальный id».

`run` возвращает то, что вернул `fn`. Если `fn` — `async`, продолжения этого промиса остаются в хранилище.

`enterWith(store)` включает хранилище для дальнейшего кода без области `fn`. Следующая независимая работа на том же ресурсе может увидеть чужой store. Для запроса оставляют `run`: вход и выход явные.

---

#### Где контекст обрывается

Хранилище сидит на асинхронных ресурсах, созданных внутри `run`. Промис, собранный снаружи и лишь разрешённый внутри, своих продолжений не переписывает: они привязаны к созданию, не к `resolve`.

```js
const als = new AsyncLocalStorage();
let resume;
const external = new Promise((r) => {
  resume = r;
});

als.run({ requestId: "r1" }, () => {
  resume("done");
});

external.then(() => {
  console.log(als.getStore()); // undefined: then висел на промисе, созданном снаружи
});
```

Граница воркера тоже обрыв: `postMessage` копирует данные (п. 97), не ALS. В воркере свой цикл и пустое хранилище, id кладут в тело сообщения.

Колбэк, который только вызвали синхронно из `run`, store видит: это тот же стек. Обрыв начинается там, где продолжение завели в другом контексте.

---

#### Предложение `AsyncContext`

`AsyncLocalStorage` — API Node, он опирается на `async_hooks`. Браузер того же глобала не имеет. Зона вроде Zone.js когда-то патчила `setTimeout`, промисы и события вручную: хрупко и расходится с движком.

Предложение `AsyncContext` описывает ту же модель в языке: переменная, `run(value, fn)`, `get` внутри `fn` и внутри продолжений после `await`. Соседний заход `run` её не видит. Пока это не общий глобал всех движков, в Node пишут `AsyncLocalStorage`, в браузере id по-прежнему тащат аргументом или замыканием на один запрос. Путать имя предложения и класс Node не стоит: вызовов `new AsyncContext.Variable()` в текущем Node нет.

---

#### Ловушка: один store на все запросы

```js
const store = { requestId: "" };

function onRequest(id) {
  store.requestId = id;
  doWork(); // любой await внутри увидит то, что успели перезаписать
}
```

Два запроса переписывают один объект. После `await` первый читает id второго. `AsyncLocalStorage` как раз чтобы так не делать. Вторая ошибка — `enterWith` в середине сервера без пары, которая контекст снимает: хвост цикла событий логирует чужой запрос.

---

#### TypeScript

`AsyncLocalStorage<T>` из `@types/node` типизирует `getStore(): T | undefined`. `undefined` в типе обязателен: снаружи `run` хранилища нет, и это легко забыть за `store.requestId`.

```ts
const als = new AsyncLocalStorage<{ requestId: string }>();

function id(): string {
  const store = als.getStore();
  if (!store) throw new Error("no request context");
  return store.requestId;
}
```

Тип не доказывает, что `run` реально обернул вызывающего. Промис, созданный снаружи, в типах выглядит так же, как созданный внутри. Предложение `AsyncContext` в lib TypeScript само не появляется, пока его нет в целевом движке.

Что сказать на собеседовании: `AsyncLocalStorage.run` вешает хранилище на продолжения, рождённые внутри колбэка. `getStore` снаружи — `undefined`. Чужой заранее созданный промис контекст не подхватывает, воркер тоже. `enterWith` без границы протекает. `AsyncContext` — языковое предложение той же идеи, не класс Node и не Zone.js.

---

### 102. Error propagation в графах промисов

О чём речь: один отказ — это не событие на шину. У каждого промиса свои реакции. `then` строит новый промис-ребро. Отказ идёт по рёбрам, на которых нет обработчика, и останавливается там, где обработчик есть. На собеседовании ловят «я же повесил `.catch`» на соседнюю ветку и ситуацию, где `await a` до `await b` бросил раньше, чем у `b` появился слушатель.

Состояния и цепочка одного промиса — п. 84. Необработанный отказ как сигнал хоста — п. 86. Здесь несколько промисов сразу.

---

#### Ребро, не шина

`p.then(onOk)` всегда создаёт новый промис. Даже без второго аргумента у `p` появляется реакция отказа: она отклоняет уже **новый** промис. Сам `p` после этого считается обработанным. Необработанным может остаться наследник.

```js
const p = Promise.reject(new Error("x"));
const child = p.then(() => console.log("ok"));
// "ok" не будет
// p обработан: then поставил реакцию отказа
// child отклонится с "x". Если на child нет catch — необработан уже child
```

Два наследника — две судьбы. `catch` одного не лечит другой.

```js
const p = Promise.reject(new Error("x"));
const a = p.then(() => {});
const b = p.catch(() => "recovered");

// b успешен
// a отклоняется тем же "x" и сам нуждается в обработчике
```

Починить ветку может только её обработчик: вернуть значение из `catch` / второго аргумента `then`. Пустой `catch` глотает отказ этой ветки и вниз пускает успех с `undefined`. Это тоже обработка, часто случайная.

---

#### Схождение

`Promise.all` подписывается на каждый вход сам. Отказ входа для `all` обработан, наружу отклоняется промис `all` первой причиной. Второй отказ входа вторым необработанным отказом не становится. Остальная работа при этом не отменяется (п. 85).

`Promise.allSettled` не отклоняет сводку из-за входа. `Promise.any` копит отказы и, если успеха не было, отдаёт один `AggregateError`. Внутри него `errors` — отдельный разбор, не один `catch` «на всё».

Ручное схождение легко теряет ветку:

```js
async function load() {
  const a = fetchA();
  const b = fetchB();
  const user = await a; // если a отказал, до await b строка не дойдёт
  return { user, extra: await b };
}
```

`b` уже запущен. Если `a` бросил на `await`, у `b` может не остаться реакции: функция вышла в отказ своего промиса, а `b` никто не читает. Оба промиса, которые стартовали, нужно дождаться в `finally` или собрать `all` / `allSettled` до первого `await` по отдельности.

```js
async function load() {
  const pending = Promise.all([fetchA(), fetchB()]);
  const [user, extra] = await pending;
  return { user, extra };
}
```

Здесь отказ любого входа становится отказом `pending`, и оба входа подписаны комбинатором.

---

#### Ловушка: `catch` не на том звене

```js
function save() {
  return write()
    .then((row) => audit(row))
    .catch(() => ({ ok: false }));
}
```

`catch` в конце ловит и отказ `write`, и отказ `audit`. Иногда аудит как раз нельзя глотать вместе с записью. Границу ставят сразу после опасного звена:

```js
function save() {
  return write()
    .catch(() => ({ ok: false }))
    .then((row) => audit(row));
}
```

Теперь отказ `audit` уходит вызывающему, отказ `write` превращается в `{ ok: false }` и в аудит уже не попадает как исключение. Вторая ловушка — `return promise` из `async`-функции мимо `try/catch` (п. 87): локальная граница не видит отказ, граф продолжается у вызывающего. Третья: несколько `then` на одном промисе ради побочных эффектов и один `catch` только на последней переменной. Остальные наследники остаются своими отказами.

---

#### Сводка

| Ситуация | Кто отклонён | Кто обработан |
|---|---|---|
| `p.then(onOk)` без `catch` на результате | новый промис | сам `p` |
| `p.then(...)` и отдельно `p.catch(...)` | ветка без своего `catch` | ветка с `catch` и сам `p` |
| `Promise.all` | сводный промис | входы, на них подписался `all` |
| `await a`, потом `await b`, `a` упал | промис функции и, возможно, `b` | только `a` |

#### TypeScript

`Promise<T>` не описывает граф. `catch` на `Promise<User>` часто сужает наследника до `Promise<User | void>` или другого объединения, если из `catch` вернули запасное значение. Это тип одной ветки. Соседний `then`, записанный в другую переменную, свой тип отказа не теряет и в компиляторе никак не связан.

`AggregateError` у `Promise.any` имеет `errors: any[]`. Разбирать причины всё равно вручную. Строгий `tsc` не требует обработать каждую ветку; это по-прежнему зона линтера висящих промисов (п. 86) и ревью графа.

Что сказать на собеседовании: отказ идёт по конкретному промису-звену. `then` без `catch` обрабатывает родителя и отклоняет ребёнка. `catch` на одной ветке соседнюю не лечит. `all` подписывается на входы сам, ручные два `await` подряд — нет: упавший первый оставляет второй запущенным и часто необработанным. Пустой `catch` тоже обработка, она превращает отказ в успех.

---

### 103. Backpressure

О чём речь: производитель делает чанки быстрее, чем потребитель их успевает записать, отрисовать или отправить в сеть. Без давления данные копятся в памяти. Backpressure — сигнал «не давай следующее, я ещё не готов». На собеседовании его показывают на потоке: `write` вернул `false`, веб-поток не зовёт `pull`, а цикл `data` без паузы память раздувает.

Потоки как типы объектов — п. 92 и п. 93. Здесь только согласование скорости.

---

#### Поток Node

У записи есть высокий уровень воды, `highWaterMark`. `writable.write(chunk)` кладёт чанк в буфер и возвращает `true`, пока буфер ниже уровня. `false` значит: буфер полон, следующие `write` лучше не звать, пока не будет `drain`.

```js
const { once } = require("node:events");

async function writeAll(writable, chunks) {
  for (const chunk of chunks) {
    const ok = writable.write(chunk);
    if (!ok) await once(writable, "drain");
  }
}
```

Игнор `false` не бросает исключение. Чанки молча копятся, процесс растёт по памяти, пока сокет не догонит.

На чтении режим `data` сам переключает поток в flowing и тащит чанки, даже если вы ещё не записали предыдущий. Честный потребитель в paused зовёт `read()` сам или ставит `pause()`, пока запись не скажет `drain`. `pipeline` это делает за вас (п. 93). Голый `pipe` давление между парой в основном соблюдает, но ошибку не довозит. Связка «и давление, и ошибка» — `pipeline`.

---

#### Веб-поток

У ридера очередь. `desiredSize` контроллера больше нуля, когда потребителю есть куда принять чанк. `pull` источника зовут в этом случае, а не на каждый чих производителя (п. 92). `pipeTo` не читает следующий чанк, пока приёмник не готов.

Своя стратегия считает размер чанка. Пока очередь выше `highWaterMark`, `pull` молчит. `enqueue` при отрицательном `desiredSize` всё ещё возможен и снова раздувает буфер: сигнал надо уважать в коде источника, API само по себе последнюю запись не всегда запрещает.

Асинхронный итератор тянет сам: следующий `next()` случается, когда потребитель дошёл до следующей итерации `for await` (п. 91). Это уже pull. Давление ломают, если заранее вычитать весь источник в массив.

---

#### Прикладная очередь

Та же схема без потокового API: в полёте не больше N операций (п. 88). Неограниченный `items.map(fn)` — производитель без `highWaterMark`. Ограниченный пул — уже backpressure на уровне задач.

Для сокета и файла пользуются сигналом потока, не своим массивом «на всякий случай». Массив между чтением и записью прячет давление: обе стороны думают, что успевают, память думает иначе.

---

#### Ловушка: `data` и `write` без `drain`

```js
readable.on("data", (chunk) => {
  writable.write(chunk); // false никто не смотрит
});
```

Быстрый файл и медленный сокет копят буфер записи. Правильно остановить чтение:

```js
readable.on("data", (chunk) => {
  const ok = writable.write(chunk);
  if (!ok) readable.pause();
});
writable.on("drain", () => readable.resume());
```

Либо отдать это `pipeline`. Вторая ловушка — `await response.text()` на огромном теле: давление есть у `response.body`, а `text()` вычитывает всё в одну строку и сигнал выбрасывает. Для большого ответа читают поток кусками.

---

#### Сводка

| Сигнал | Среда | Что сделать |
|---|---|---|
| `write` вернул `false` | Node | ждать `drain`, не писать дальше |
| `pause` / `resume` | Node readable | не копить `data` |
| `desiredSize` / `pull` | веб-поток | не `enqueue`, пока размер отрицательный |
| пул N | свои промисы | не стартовать N+1 |
| `for await` | итератор | не вычитывать источник заранее |

#### TypeScript

`writable.write` в типах Node возвращает `boolean`. Компилятор не заставляет этот `boolean` прочитать: вызов «ради побочного эффекта» типов законен, давление при этом потеряно. `desiredSize` — `number | null`, `null` когда поток уже ошибся или закрыт. Стратегия `QueuingStrategy<T>` стирается вместе с размером чанка. Никакой тип не оценивает байты в рантайме.

Что сказать на собеседовании: backpressure — не читать и не писать следующий чанк, пока потребитель не готов. В Node это `false` из `write` и `drain`, в веб-потоке — `pull` и `desiredSize`. `pipeline` и `pipeTo` сигнал соблюдают. `on("data")` плюс `write` без паузы память копит молча. Вычитать всё в массив или в `text()` давление отменяет.

### 104. Debounce / throttle / leading-trailing

О чём речь: событие ввода, скролла или ресайза приходит чаще, чем имеет смысл работать. Debounce ждёт паузу в потоке вызовов и тогда выполняет функцию один раз. Throttle выполняет не чаще, чем раз в окно времени, даже если вызовы льются непрерывно. Leading и trailing говорят, сработать в начале окна, в конце или с обоих краёв. На собеседовании просят написать trailing-debounce и объяснить, чем он не throttle.

Оба приёма ставят таймер. Это задача event loop (п. 83), не микрозадача: пока окно не вышло, стек свободен.

---

#### Debounce

Каждый вызов сдвигает срок. Функция бежит, когда вызовы замолчали на `ms`. Это trailing: важен последний аргумент, промежуточные пропадают.

```js
function debounce(fn, ms) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = undefined;
      fn.apply(this, args);
    }, ms);
  };
}
```

Leading-debounce срабатывает сразу на первом вызове серии, потом молчит, пока серия не прервётся на `ms`. Хвост серии отдельным вызовом не повторяют.

```js
function debounceLeading(fn, ms) {
  let timer;
  return function (...args) {
    if (!timer) fn.apply(this, args);
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = undefined;
    }, ms);
  };
}
```

Поиск по вводу обычно trailing: запрос уходит с финальной строкой, не с первой буквой. Кнопка, которую надо принять сразу и игнорировать дребезг, — leading.

---

#### Throttle

Вызовы не прекращаются: скролл идёт секундами. Throttle гарантирует период. Простой leading: первый вызов сразу, следующие в окне игнорируются, окно меряют от последнего принятого.

```js
function throttleLeading(fn, ms) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= ms) {
      last = now;
      fn.apply(this, args);
    }
  };
}
```

У этого варианта нет хвоста. Последний скролл окна может не обработаться, если он попал внутрь `ms`. Trailing добавляет таймер на конец окна и вызывает функцию с последними аргументами. Leading и trailing вместе: сразу первый, и ещё раз в конце, если внутри окна были подавленные вызовы. Так устроены опции `leading` / `trailing` в библиотечных реализациях. `maxWait` у debounce — потолок: даже если паузы всё нет, сработать хотя бы раз в N мс. Это уже гибрид с throttle.

Для кадра скролла окно иногда не таймер, а `requestAnimationFrame` (п. 95): не чаще одного раза на отрисовку. Таймер на 16 мс к vsync не привязан.

---

#### Ловушка: таймер после того, как работа не нужна

```js
const onInput = debounce((q) => search(q), 300);
input.addEventListener("input", (e) => onInput(e.target.value));
```

Если узел сняли, таймер всё ещё может вызвать `search` через 300 мс. В обёртке нужен `cancel`, который делает `clearTimeout`. Тот же `clearTimeout` на сигнале отмены (п. 89).

Вторая ловушка — перепутать приёмы на живом потоке. Debounce во время непрерывного скролла не сработает никогда: паузы нет, таймер вечно сдвигается. Там throttle. Наоборот, throttle на строке поиска шлёт запрос посреди набора, хотя пользователь ещё печатает.

Третья: аргументы и `this`. В trailing в функцию попадают аргументы **последнего** вызова, не первого. `fn()` без `apply` теряет `this` метода (п. 34). Обёртка, созданная один раз, замыкает тот `fn`, который передали в `debounce`. Если снаружи подменили функцию, старая обёртка этого не узнает.

---

#### Сводка

| | Когда вызывает | Пока события льются без паузы |
|---|---|---|
| Debounce trailing | один раз после тишины `ms` | не вызывает |
| Debounce leading | сразу, потом тишина до паузы | повторно не вызывает |
| Throttle leading | не чаще раза в `ms`, с начала окна | вызывает по периоду |
| Throttle trailing | на конце окна с последними аргументами | вызывает по периоду |
| Leading + trailing | первый сразу и последний на границе окна | оба края |

#### TypeScript

Обёртку обобщают, чтобы аргументы не стали `any[]`.

```ts
function debounce<A extends unknown[]>(
  fn: (...args: A) => void,
  ms: number,
): ((...args: A) => void) & { cancel: () => void } {
  let timer: ReturnType<typeof setTimeout> | undefined;
  const wrapped = (...args: A) => {
    if (timer !== undefined) clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
  wrapped.cancel = () => {
    if (timer !== undefined) clearTimeout(timer);
  };
  return wrapped;
}
```

`ReturnType<typeof setTimeout>` в DOM — `number`, в Node — `NodeJS.Timeout` (п. 82). Общий файл под обе среды на голом `number` ломается. Тип не говорит, leading это или trailing: это разные функции, не флаг, который компилятор проверит в рантайме. Возврат `fn`, если он промис, обёртка выше выбрасывает: для поиска с `await` отказ внутри `fn` легко остаётся необработанным (п. 86). Тогда `fn` возвращает `Promise<void>`, а обёртка вешает `.catch` сама или возвращает промис только у trailing-вызова, который реально запустила.

Что сказать на собеседовании: debounce ждёт тишину, throttle режет частоту, пока поток не замолкает. Trailing берёт последний аргумент, leading срабатывает сразу. Непрерывный скролл debounce не выпускает. Таймер снимают `cancel`, `this` передают через `apply`. Обёртка замыкает тот `fn`, который дали при создании.

### 105. Scheduler / yielding long tasks (`scheduler.yield`)

О чём речь: задача длиннее примерно 50 мс на главном потоке — long task. Пока она держит стек, кадр не рисуется и ввод не обрабатывается (п. 81, п. 95). `scheduler.yield` — явная пауза внутри такой работы: стек отпускают, браузер может отрисовать и принять клик, потом продолжение возвращается. На собеседовании отличают этот yield от `queueMicrotask`, который кадр как раз не отпускает (п. 83, п. 99).

API приоритетов — `scheduler.postTask`. `yield` — короткая уступка из уже идущей задачи, без отдельной очереди на каждый кусок.

---

#### Уступить кадр

`scheduler.yield()` возвращает промис. `await` на нём ставит продолжение так, чтобы цикл успел взять отрисовку и ввод, и только потом снова ваш код. Приоритет продолжения наследует текущую задачу, а не падает в самый фон.

```js
async function indexAll(items) {
  for (const item of items) {
    heavy(item); // синхронный кусок короче бюджета кадра
    await scheduler.yield();
  }
}
```

Кусок между двумя `yield` остаётся синхронным. Если `heavy` сам на 200 мс, yield после него кадр уже пропустил. Режут работу так, чтобы один кусок уложился в бюджет, а не вставляют yield «для галочки» после гигантской функции.

`queueMicrotask` и голый `await Promise.resolve()` продолжение оставляют в микрозадачах. Следующий кусок обойдёт отрисовку. Для длинного цикла это голодание paint (п. 99). `setTimeout(fn, 0)` кадр отпускает, но это другая задача: задержка снизу зажимается (п. 82), приоритета у неё нет, порядок с вводом не обещан.

`scheduler.postTask(fn, { priority })` ставит отдельную задачу. Приоритеты: `user-blocking`, `user-visible`, `background`. Фон уступает вводу и кадру. `yield` внутри фоновой задачи продолжает её приоритет. Смешивать «всё через `background`» и расчёт, который пользователь ждёт на экране, нельзя: фоновое легко откладывается, пока крутится анимация.

---

#### Запасной путь

`scheduler.yield` есть в Chromium и расходится по остальным движкам не одновременно. Перед вызовом проверяют метод. Запасной ход — задача, не микрозадача.

```js
function yieldToMain() {
  if (globalThis.scheduler?.yield) return scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}
```

`setTimeout(0)` грубее: минимум несколько миллисекунд после вложенных таймеров и никакого наследования приоритета. Это запасной ход, не тот же контракт. `requestIdleCallback` (п. 95) сюда не подставляют: он про простой, а не про «вернись сразу после кадра». `requestAnimationFrame` привязан к отрисовке и в фоновой вкладке замирает.

`scheduler.yield` на главном потоке окна. В Node этого планировщика страницы нет: там уступка — `setImmediate` или разбиение на задачи цикла (п. 82). Тяжёлое, что не обязано быть в окне, по-прежнему уносят в worker (п. 96), а не режут yield-ами навсегда.

---

#### Ловушка: yield слишком редкий и yield в микрозадаче

```js
async function bad(items) {
  for (const item of items) heavy(item); // один long task на весь массив
  await scheduler.yield();
}
```

Один `await` после цикла ничего не спас: кадр замер на всё время `for`. Yield ставят между короткими кусками.

Вторая ошибка — «дробить» через `queueMicrotask` и считать, что это `scheduler.yield`. Ввод так и не войдёт. Третья: бесконечный цикл с yield, но каждый кусок снова кладёт работу, без условия выхода. Страница живая и всё равно никогда не заканчивает операцию. Уступка не отменяет алгоритм, она только возвращает стек.

`isInputPending`, где он есть, отвечает, ждёт ли ввод, и им иногда решают, пора ли уступать раньше конца куска. Это подсказка, не замена `yield`: сам по себе опрос флага стек не отпускает.

---

#### Сводка

| Приём | Отпускает paint и ввод | Чем отличается |
|---|---|---|
| синхронный цикл | нет | один long task |
| `queueMicrotask` / `await Promise.resolve()` | нет | микрозадачи до отрисовки |
| `setTimeout(0)` | да | грубая задача, кламп, без приоритета |
| `scheduler.yield()` | да | продолжение с приоритетом текущей задачи |
| `postTask(..., { priority: "background" })` | да | отдельная фоновая задача |
| worker | да, для окна | другой агент, не нарезка главного потока |

#### TypeScript

`scheduler` приходит из свежего DOM lib. В старом `lib` метода `yield` нет, хотя Chromium его уже имеет: типы отстают от движка, вызов типизируют локально, не через `any` на весь `window`.

```ts
function canYield(s: unknown): s is { yield(): Promise<void> } {
  return typeof s === "object" && s !== null && "yield" in s && typeof s.yield === "function";
}
```

Предикат (п. 75) здесь уместен: наличие метода — рантайм, после сужения `await scheduler.yield()` законен. Тип промиса не говорит, что продолжение именно задача отрисовки, а не микрозадача. В Node-проекте без DOM `scheduler` в типах отсутствует специально.

Что сказать на собеседовании: long task держит главный поток, кадр и ввод ждут. `scheduler.yield` отпускает стек до продолжения с тем же приоритетом. `queueMicrotask` так не уступает. `setTimeout(0)` уступает грубее и без приоритета. Резать надо между короткими кусками. Нет метода — проверяют в рантайме и падают на таймер. Совсем чужую тяжёлую работу уносят в worker.
