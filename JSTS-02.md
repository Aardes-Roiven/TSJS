# Область видимости, выполнение, `this`

Детализация секции 2 из [JSTS.md](./JSTS.md).

Конспект для собеседования: в каждой теме сначала **о чём речь и зачем спрашивают**, потом устройство, ловушки и TypeScript.

---

### 31. Lexical scope, scope chain, global object

О чём речь: когда в коде написано имя `x`, движок должен понять, **какая именно переменная** имеется в виду. JavaScript отвечает на это по **месту, где код написан**, а не по тому, кто функцию вызвал. Это лексическая (статическая) область видимости. Без неё не объяснить замыкания, модули и «почему колбэк видит `y` из внешней функции».

---

#### Что такое scope

Scope — набор имён, доступных в данной точке программы. Имя — это коробка (binding): «`x` сейчас указывает на вот это значение».

Вложенность областей — матрёшка:

```
блок { } внутри функции
  → функция
    → модуль (ESM) или скрипт
      → глобальный объект (если до него вообще доходят)
```

Поиск идёт **только наружу**. Внутренняя функция видит внешние имена. Внешняя **не** видит имена внутренней.

```js
const x = 1; // модуль / скрипт

function outer() {
  const y = 2; // область outer

  function inner() {
    const z = 3; // область inner
    return x + y + z;
  }

  return inner;
}

outer()(); // 6
```

`inner` берёт `z` у себя, `y` у `outer`, `x` снаружи `outer`. Если вызвать `inner` через час в другом файле, цепочка **не изменится**: она зафиксирована в момент создания функции.

Это не динамический scope (как в Bash: кто вызвал, того переменные). В JS неважно, что `inner` вызвали из `setTimeout` или из чужого модуля.

---

#### Scope chain на пальцах

Каждая функция помнит ссылку на **внешнее лексическое окружение**. Цепочка этих ссылок — scope chain.

Когда выполняют `return x + y`:

1. Есть ли `x` в `inner`? Нет.
2. Есть ли в `outer`? Нет.
3. Есть ли в модуле? Да, `1`.

Первое найденное имя побеждает. Внутреннее `const x` **затеняет** внешнее (shadowing), внешнее в этой зоне просто не видно.

`this` в эту цепочку **не входит**. Имя `x` ищут по scope; `this` подставляют по правилам вызова (п. 34). Можно знать все переменные и всё равно потерять `this`.

---

#### Глобальный объект

Конец цепочки в обычном **скрипте** (файл без `import`/`export`, классический `<script>`):

- браузер: `window`, он же `globalThis`
- Node (CommonJS): `global` / `globalThis`
- worker: свой глобал, не `window`, но `globalThis` есть

`var x = 1` и `function f() {}` на верхнем уровне скрипта становятся и локальным именем, и **свойством глобала**: `window.x`, `window.f`.

`let` / `const` / `class` на верхнем уровне скрипта живут в отдельном script scope: имя есть, **свойства `window` нет**.

```html
<script>
  var a = 1;
  let b = 2;
  console.log(window.a); // 1
  console.log(window.b); // undefined
</script>
```

`globalThis` — переносимый способ: один код для браузера, Node и worker.

---

#### Модуль — не глобал

Файл с `import`/`export` (и `"type": "module"`) имеет **свою** область на весь файл. Верхний `var` **не** садится на `window`. Соседний модуль эти имена не видит, пока не импортирует.

Поэтому в приложении со сборщиком «положить переменную в `window` просто объявлением» не получится. Нужен явный `globalThis.foo = ...` (обычно не нужно).

Top-level `this` в модуле — `undefined`, не `window`.

---

#### TypeScript

Области те же. Тип имени виден там же, где значение. Нюанс: сужение `let` во внешней функции часто **не проходит** во внутреннюю: компилятор не уверен, что до вызова колбэка значение не сменили. Это следствие лексики + мутабельного binding, не отдельная фича.

Что сказать на собеседовании: поиск имени — по месту написания, наружу по цепочке. Глобал — дно у скрипта; модуль до глобала не доходит своими `var`. `this` — другая система.

---


### 32. Hoisting, TDZ, `var` / `let` / `const`

О чём речь: три способа объявить переменную. Они отличаются **где имя видно**, **что происходит до строки объявления** и **можно ли потом присвоить заново**. На собеседовании почти всегда просят сравнить их и объяснить цикл с `setTimeout`.

Сначала общая модель. Движок не «перетаскивает строку `var a = 1` наверх». У области видимости две фазы: сначала зарегистрировать имена, потом выполнять код сверху вниз. Разница `var` / `let` / `const` — в том, **какой ширины область** и **готово ли имя к чтению сразу после регистрации**.

---

#### Где имя видно (область)

`var` живёт в **функции** (или в скрипте/глобале, если функции нет). Фигурные скобки `if` / `for` / голый блок его **не закрывают**.

```js
function f() {
  if (true) {
    var x = 1;
  }
  console.log(x); // 1 — блок if не спрятал var
}
```

`let` и `const` живут в **блоке** `{ ... }`. Снаружи блока имени нет.

```js
function f() {
  if (true) {
    let x = 1;
    const y = 2;
  }
  console.log(x); // ReferenceError
  console.log(y); // ReferenceError
}
```

Это главное бытовое отличие. Счётчик цикла, временная переменная внутри `if`, имя, которое не должно торчать ниже по функции — `let`/`const`. `var` «вытечет» из `if` и из `for` на всю функцию.

На верхнем уровне **скрипта** (не модуля): `var x = 1` ещё и делает `window.x`. `let` / `const` на `window` не садятся. В ES-модуле ни то ни другое не становится свойством `window`.

Повторное объявление в одной области:

```js
var a = 1;
var a = 2; // можно, это та же переменная

let b = 1;
let b = 2; // SyntaxError

const c = 1;
const c = 2; // SyntaxError
```

---

#### Что видно *до* строки объявления

Объявление регистрируют заранее. Вопрос — можно ли читать имя, пока выполнение не дошло до `= ...`.

**`var` поднимается и сразу равен `undefined`.** Переменная уже существует, просто значение ещё не присвоили:

```js
console.log(a); // undefined, не ошибка
var a = 1;
console.log(a); // 1
```

Движок как будто делает в начале функции `var a;` (то есть `a = undefined`), а на старом месте оставляет только `a = 1`.

**`let` и `const` тоже «поднимаются» как имена**, но до своей строки находятся в **Temporal Dead Zone (TDZ)**: зона, где имя уже занято, а читать/писать ещё нельзя. Любое обращение — `ReferenceError`:

```js
console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 1;
```

Не «переменной нет» (`typeof notDeclared === "undefined"`). Переменная **есть**, но ещё не родилась. Поэтому `typeof` здесь не спасает:

```js
typeof notDeclared; // "undefined" — имени вообще нет
typeof c;           // ReferenceError — имя c уже в TDZ
const c = 1;
```

TDZ заканчивается в момент выполнения объявления (`let b = 1` или `let b` без значения — тогда `b` станет `undefined`, но уже легально).

Если внутренний блок объявляет то же имя, внешнее **не используется**, пока внутреннее в TDZ. Это не баг, а затенение (shadowing):

```js
const x = 1;
{
  console.log(x); // ReferenceError, не 1
  let x = 2;      // этот x уже «занял» имя во всём блоке
}
```

Пока не дошли до `let x = 2`, внутренний `x` мёртв, а внешний `x` этим именем в блоке не виден.

---

#### Можно ли присвоить ещё раз: `let` vs `const`

`var` и `let` — переприсваивать binding можно:

```js
var a = 1;
a = 2; // ок

let b = 1;
b = 2; // ок
```

`const` — **нельзя сменить привязку**. Значение должно быть указано сразу, пустого `const x;` нет.

```js
const n = 1;
n = 2; // TypeError

const m; // SyntaxError: нет инициализатора
```

«Константа» здесь про **имя**, не про внутренности объекта. Ссылка в коробке `obj` не меняется, содержимое объекта — сколько угодно:

```js
const obj = { x: 1 };
obj.x = 2;  // можно: тот же объект, другое поле
obj = {};   // TypeError: пытаемся положить в коробку другой объект
```

То же с массивом: `arr.push(1)` можно, `arr = []` нельзя.

Неизменяемость полей — это `Object.freeze` / `readonly` в TS, не `const`.

---

#### Цикл и замыкание — зачем это спрашивают

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// печатает 3, 3, 3
```

`var i` одна на всю функцию. Три таймера закрыли **одну и ту же** `i`. Когда они сработают, цикл уже кончился, `i === 3`.

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// печатает 0, 1, 2
```

`let` в `for` на **каждую итерацию** делает новую привязку `i`. Каждый колбэк держит свою. `const` в `for (const x of arr)` ведёт себя так же по итерациям.

Это не «магия setTimeout». Любое замыкание внутри цикла с `var` увидит финальное значение.

---

#### Сводка

| | `var` | `let` | `const` |
|---|---|---|---|
| Область | функция / скрипт | блок `{ }` | блок `{ }` |
| До строки объявления | `undefined` | TDZ, ошибка | TDZ, ошибка |
| Переприсвоить имя | да | да | нет |
| Мутировать объект | да | да | да (тот же объект) |
| Повтор `var x` / `let x` | можно | ошибка | ошибка |
| На `window` в скрипте | да | нет | нет |
| В цикле + замыкание | одна переменная | своя на итерацию | своя на итерацию |

Практика: по умолчанию `const`. Если имя нужно переприсвоить (`let count = 0; count += 1`) — `let`. `var` в новом коде не писать.

В TypeScript то же в рантайме. На типы влияет так: `const x = "a"` выводится как литерал `"a"`; `let x = "a"` — как `string`. `const obj = { a: 1 }` не делает поля `readonly`.

Что сказать на собеседовании: `var` — функция, живёт с `undefined` с начала области, в цикле одна на всех. `let`/`const` — блок и TDZ. Разница `let` и `const` только в переприсваивании имени, не в иммутабельности объекта.

---

### 33. Closures: lifetime, утечки, модульный паттерн

О чём речь: функция может читать и менять переменные **внешней** области даже после того, как внешняя функция уже закончилась. Связка «функция + её внешние коробки» называется замыканием. На собеседовании ждут определение, пример со счётчиком, баг цикла и хотя бы слово про память.

---

#### Как это выглядит

```js
function makeCounter() {
  let n = 0;
  return function inc() {
    n += 1;
    return n;
  };
}

const a = makeCounter();
const b = makeCounter();

a(); // 1
a(); // 2
b(); // 1 — свой n, не общий с a
```

`makeCounter` вернула `inc` и «умерла». Стек кадра нет, но коробка `n` жива: на неё ссылается `inc`. Пока жив `a`, жив и его `n`. У `b` отдельный вызов `makeCounter` — отдельная коробка.

Замыкание — не «функция внутри функции». Это факт, что внутренняя функция **использует** внешние binding. Если не использует — формально окружение могут выкинуть (движок оптимизирует).

---

#### Захватывается коробка, не снимок

```js
let x = 1;
const f = () => x;
x = 2;
f(); // 2
```

`f` не запомнила «единицу на момент создания». Она каждый раз читает текущее содержимое коробки `x`. Отсюда баг с `var` в цикле: все таймеры смотрят в одну `i`, к моменту срабатывания там уже `3`.

Если нужен снимок — своя коробка на итерацию (`let` в `for`) или аргумент:

```js
for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(() => console.log(j), 0);
  })(i);
}
```

Старый трюк IIFE: параметр `j` — новая коробка со значением этой итерации.

---

#### Зачем это нужно

- **Фабрика:** `makeCounter`, `makeUrl(base)`, обработчик с захваченным `id`.
- **Инкапсуляция:** снаружи нет `secret`, есть только методы. Это модульный паттерн:

```js
const api = (function () {
  let secret = 0;
  return {
    inc() { secret += 1; },
    get() { return secret; },
  };
})();

api.get(); // 0
// secret снаружи нет
```

ES-модуль делает то же областью файла: не экспортировали — не видно. IIFE был костылём, пока модулей не было.

- **Частичное применение:** `const add1 = (b) => add(1, b)` замыкает `1`.

---

#### Lifetime и утечки

Коробка живёт, **пока жива хотя бы одна функция**, которая из неё читает (и пока движок не доказал обратное).

Долгоживущие вещи:

- слушатель `addEventListener` без `remove`
- `setInterval` без `clearInterval`
- подписка (store, WebSocket, Observable) без unsubscribe
- кеш «навсегда» в замыкании модуля

Типичная утечка: в `makeHandler` закрыли большой `data` (мегабайтный массив), повесили handler на кнопку. Кнопку не сняли — массив не соберёт GC, хотя снаружи `data` уже «не нужен».

Не обязательно держится *вся* внешняя функция целиком: современные движки могут удерживать только используемые binding. На это нельзя полагаться в голове «ну V8 умный»: если в замыкании фигурирует объект, считайте, что он жив.

В React то же: `useEffect(() => { ... }, [])` замыкает props того рендера. Нет cleanup — подписка и старые значения висят. Зависимости и cleanup — про lifetime замыкания.

---

#### TypeScript

Новых типов замыкание не создаёт. Ломает **narrowing**:

```ts
function f(x: string | number) {
  if (typeof x === "string") {
    setTimeout(() => {
      x.toUpperCase(); // часто ошибка: x снова string | number
    }, 0);
  }
}
```

Компилятор не верит, что до колбэка `x` не присвоили заново. Снимок: `const s = x` внутри `if` после сужения.

Что сказать на собеседовании: замыкание — функция плюс лексические коробки. Живёт, пока жива функция. Захват binding, не копии. Польза — модуль и фабрика; цена — удержание памяти.

### 34. `this` в функциях, методах, колбэках, strict mode

О чём речь: `this` — скрытый аргумент **вызова**, не переменная из scope. У ordinary function его значение решается в момент `fn(...)`, а не когда функцию написали. Потерянный метод и колбэк — самый частый вопрос после `var`/`let`.

Стрелки здесь не главные: у них `this` лексический (п. 35). Ниже — **function / method / class method**.

---

#### Правила ordinary function

Смотрят, **как вызвали**:

| Вызов | `this` |
|---|---|
| `obj.method()` | `obj` (левая часть точки) |
| `obj.a.b()` | `obj.a` |
| `fn()` голый, sloppy | глобал (`window`) |
| `fn()` голый, strict / class / module | `undefined` |
| `new Fn()` | новый объект (п. 37) |
| `fn.call(x)` / `apply` / `bind` | явно `x` (у bind — навсегда) |
| DOM `el.addEventListener("click", fn)` | обычно `el` (не стрелка) |

Не смотрят, в каком объекте функция лежала в исходнике. Смотрят вызов.

```js
const user = {
  name: "Anna",
  hi() {
    return this.name;
  },
};

user.hi(); // "Anna" — вызов через user

const hi = user.hi;
hi(); // this не user: в strict TypeError на this.name, в sloppy window.name
```

В `hi` лежит та же функция. Точки слева нет — контекст потерян.

---

#### Колбэки

Движок вызывает вашу функцию как `fn()` или как `fn.call(element)`:

```js
setTimeout(user.hi, 0);           // голый вызов → this не user
button.addEventListener("click", user.hi); // this часто button
arr.forEach(user.hi);             // this не user (если не передали 2-й аргумент)
```

Как лечить:

```js
setTimeout(() => user.hi(), 0);
setTimeout(user.hi.bind(user), 0);
```

В классе поле-стрелка `hi = () => this.name` тоже фиксирует экземпляр (цена — функция на каждый объект).

`forEach` принимает второй аргумент `thisArg`. `addEventListener` — нет, только bind/обёртка.

---

#### Вложенная function не наследует this

```js
const obj = {
  outer() {
    function inner() {
      return this;
    }
    return inner(); // голый вызов
  },
};

obj.outer(); // inner: undefined в strict, не obj
```

`outer` имеет `this === obj`, `inner` — нет. Старый код: `const self = this`. Нормальный: стрелка внутри `outer`.

Методы `class` всегда strict: `const m = instance.method; m()` → `this === undefined`.

---

#### TypeScript

У метода класса `this` — экземпляр. Можно описать контракт вызова:

```ts
function greet(this: { name: string }, punct: string) {
  return this.name + punct;
}

greet("!");                    // ошибка: нет this
greet.call({ name: "A" }, "!"); // ок
```

Первый параметр с именем `this` в JS не существует, это только проверка.

`noImplicitThis` ругается на `this` в функции без типа.

Что сказать на собеседовании: ordinary `this` = кто вызвал. Сорвали с объекта — контекст умер. В strict голый вызов даёт `undefined`, не `window`. Колбэк почти всегда обёртка или `bind`.

---

### 35. Arrow functions vs regular: `this`, `arguments`, `new`, prototype

О чём речь: `() => {}` — не сахар над `function () {}`. Четыре дырки: свой `this`, `arguments`, `new`, `.prototype`. Стрелку ставят туда, где динамический `this` мешает.

---

#### this лексический

Стрелка **не получает** `this` от вызова. Она читает `this` окружающей ordinary function / класса, как обычную переменную из scope.

```js
const obj = {
  name: "Anna",
  hi() {
    const inner = () => this.name;
    return inner();
  },
};

obj.hi(); // "Anna"
inner.call({ name: "X" }); // если достать inner — всё равно Anna: call не действует
```

`.call` / `.apply` / `.bind` **не меняют** `this` стрелки (bind всё же может пришить аргументы).

Поле класса:

```js
class User {
  name = "Anna";
  hi = () => this.name;
}

const u = new User();
setTimeout(u.hi, 0); // "Anna" — this уже замкнут
```

Каждый экземпляр имеет **свою** функцию `hi` в поле, не одну на `User.prototype`. Методы `hi() {}` в классе живут на прототипе (дешевле), но для `setTimeout(u.hi)` нужен bind.

Стрелка **вместо метода литерала** обычно ошибка: окружающий `this` — не этот объект.

```js
const obj = {
  name: "Anna",
  hi: () => this.name, // модуль: this === undefined
};

obj.hi(); // не "Anna"
```

---

#### arguments

У стрелки объекта `arguments` нет. Пишут rest:

```js
const f = (...args) => args;
```

Если стрелка сидит внутри `function`, слово `arguments` найдёт **внешнюю** ordinary function. Легко прочитать не те аргументы.

---

#### new и prototype

```js
const F = () => {};
new F();        // TypeError: F is not a constructor
F.prototype;    // undefined
```

Ordinary function:

```js
function F() {}
F.prototype;    // { constructor: F }
new F();        // ок
typeof F.prototype; // "object"
```

Стрелка не участвует в `[[Construct]]`. Конструктор и «класс без class» — только `function` / `class`.

---

#### Когда что

| Нужно | Что взять |
|---|---|
| колбэк, сохранить this класса/метода | стрелка |
| короткая чистая функция | стрелка |
| метод на прототипе, `obj.method()` как API | ordinary / class method |
| конструктор | `function` / `class`, не стрелка |
| динамический this (плагин вызвал как метод) | ordinary |
| `arguments` | ordinary или rest у стрелки |

В TypeScript типы `(x: number) => void` часто совпадают. Разница в construct signature (`new (...) => T`) и в `this`.

Что сказать на собеседовании: стрелка захватывает this с места написания, не конструктор, нет arguments и prototype. Метод объекта — обычно не стрелка; колбэк — часто стрелка.

---

### 36. `call` / `apply` / `bind`, partial application

О чём речь: явно задать функции `this` и часть аргументов. Методы живут на `Function.prototype`. Путают с `Object.prototype`. На собеседовании просят отличить три штуки и объяснить `hasOwnProperty.call`.

---

#### Три вызова

```js
function greet(punct) {
  return this.name + punct;
}

const user = { name: "Anna" };

greet.call(user, "!");           // "Anna!" — вызвать сейчас, args списком
greet.apply(user, ["!"]);        // "Anna!" — args массивом
const g = greet.bind(user, "!"); // новая функция
g();                             // "Anna!"
```

**`call(thisArg, ...args)`** — выполнить сразу.  
**`apply(thisArg, argsArray)`** — сразу, аргументы из массива / array-like. После `fn.call(ctx, ...arr)` почти не нужен; ещё жив для `Math.max.apply(null, nums)` в старом коде (лучше `Math.max(...nums)`).  
**`bind(thisArg, ...partialArgs)`** — **не вызывает**. Возвращает новую функцию с пришитым `this` и уже подставленными первыми аргументами. Исходная `greet` не меняется.

Повторный bind:

```js
const g1 = greet.bind(user);
const g2 = g1.bind({ name: "Bob" });
g2("!"); // всё ещё Anna: this у bound function второй bind не перебивает
```

Аргументы второго bind **добавляются**, this — нет.

---

#### Partial application

Зафиксировать префикс аргументов:

```js
function add(a, b, c) {
  return a + b + c;
}

const add1 = add.bind(null, 1);
add1(2, 3); // 6
```

`null` как thisArg, когда this не важен. Каррирование «по одному аргументу» чаще пишут руками или библиотекой, не `bind`.

---

#### Чужой метод на чужом this

```js
Object.prototype.hasOwnProperty.call(obj, "x");
Object.prototype.toString.call(value); // "[object Array]"
Array.prototype.slice.call(arguments);
```

Берут функцию `hasOwnProperty` (это function, у неё есть `.call`) и говорят: выполнись, будто `this` это `obj`.

Зачем не `obj.hasOwnProperty("x")`:

- у `obj` поле `hasOwnProperty` могут перезаписать;
- `Object.create(null)` — нет прототипа, метода нет вообще.

`call` здесь не «магия Object.prototype.call» — такого метода нет. Есть `Function.prototype.call` у самой функции-метода.

---

#### Стрелки и new

`arrow.call(x)` this стрелки не меняет.  
`boundFn` можно `new`: тогда this — новый экземпляр, а пришитые bind-аргументы остаются (редко нужно, путает).

В TypeScript после `bind` из типа вычитаются пришитые параметры (`CallableFunction.bind`). Явный `this` в сигнатуре заставляет вызывать через `call`/`bind`.

Что сказать на собеседовании: call/apply — сейчас с данным this; bind — новая функция. Partial — первые аргументы на bind. `Proto.method.call(x)` — применить метод к x, у которого своего честного метода нет.

---

### 37. `new`, `[[Construct]]`, `[[Call]]`

О чём речь: одну и ту же ordinary function можно вызвать как функцию и как конструктор. Внутри это разные операции: `[[Call]]` и `[[Construct]]`. Class разрешает только construct. Стрелка — только call.

---

#### Что делает `new Fn(a, b)`

Упрощённо:

1. Создать `{}`.
2. Поставить ему прототип `Fn.prototype` (`Object.getPrototypeOf(obj) === Fn.prototype`).
3. Вызвать `Fn` с `this =` этот объект и аргументами `a, b`.
4. Если `Fn` вернула **объект** (в т.ч. функцию, массив) — наружу **она**, шаг 1 выкидывают.
5. Если вернула примитив или `undefined` — наружу объект с шага 1.

```js
function User(name) {
  this.name = name;
}

const u = new User("Anna");
u.name; // "Anna"
u instanceof User; // true
```

Подмена результата:

```js
function Weird() {
  this.x = 1;
  return { fake: true };
}

new Weird(); // { fake: true } — this.x потерялся
```

Так иногда пишут «синглтон» или обходят `this`. В нормальном конструкторе `return` объекта нет.

---

#### Call без new

```js
User("Anna");
```

Это `[[Call]]`. `this` по правилам п. 34: в sloppy — глобал (`window.name = "Anna"`), в strict — `undefined` (присвоение полю упадёт).

Старый паттерн «можно с new и без»:

```js
function User(name) {
  if (!(this instanceof User)) {
    return new User(name);
  }
  this.name = name;
}
```

Класс так не работает:

```js
class User {
  constructor(name) { this.name = name; }
}

User("Anna"); // TypeError
```

---

#### new.target

Внутри функции:

- вызвали `new User` → `new.target === User` (или наследник, если `new Child`)
- вызвали `User()` → `new.target === undefined`

Так отличают construct от call без `instanceof` (который ломается чужим prototype).

Стрелка: нет `[[Construct]]`, `new (() => {})` — TypeError, своего `new.target` нет (берёт внешний, если внутри конструктора).

---

#### TypeScript

```ts
type Ctor = new (name: string) => User;
type Call = (name: string) => void;
```

Это разные типы. `typeof User` после `class User` — конструктор. `InstanceType<typeof User>` — экземпляр. Перегрузки call + construct описывают библиотеки вроде jQuery.

Что сказать на собеседовании: new создаёт объект, цепляет Fn.prototype, вызывает Fn как this, отдаёт объект (или то, что return-объект). Class только через new. Call и construct — разные внутренние слоты.

---

### 38. Strict mode: отличия поведения

О чём речь: strict превращает старые тихие сюрпризы в ошибки и меняет `this`. Модули и классы **уже** strict: отдельная директива в новом коде часто не нужна. На собеседовании не таблица из MDN, а 5–6 эффектов, которые ловят в проде.

---

#### Как включить

```js
"use strict"; // первой строкой скрипта или функции
```

Всегда strict, директива не нужна:

- ES-модуль
- тело `class` (методы и конструктор)
- некоторые движковые контексты

Директива в функции не делает strict весь файл — только эту функцию (и вложенные, если не оговорено иначе). Вложенная без своей директивы в strict-родителе тоже strict.

---

#### Что меняется на практике

**1. Голый `this`.** `fn()` → `undefined`, не `window`. Потерянный метод падает на `this.foo`, а не пишет в глобал.

**2. Неявный глобал.**

```js
"use strict";
x = 1; // ReferenceError, не window.x
```

Опечатка в имени становится ошибкой, а не свойством `window`.

**3. `delete` имени.**

```js
var a = 1;
delete a; // в strict ошибка; delete obj.prop по-прежнему для свойств
```

**4. Дубли параметров.** `function f(a, a) {}` — SyntaxError. В sloppy второй `a` побеждал, путаница с `arguments`.

**5. `with (obj) { x = 1 }`** — запрещён. Непонятно, `obj.x` это или глобал.

**6. `arguments` и параметры развязаны.**

```js
function f(a) {
  arguments[0] = 99;
  return a; // sloppy: 99; strict: исходный a, не 99
}
```

Плюс лучше rest: `(...args)`.

**7. `eval`.** В strict не создаёт `var` в окружающей функции так же свободно: у eval своя область.

**8. `arguments.callee`** — ошибка. Рекурсия — по имени функции или `function foo()`.

**9. Октальные литералы.** `010` в sloppy было 8; в strict — ошибка. Пишут `0o10`.

Присваивание `undefined = 1` в глобале в strict не проходит (в sloppy тихо игнорировалось или ломалось).

---

#### Это не tsconfig strict

`strict: true` в TypeScript — набор проверок типов (`strictNullChecks` и др.). JS-директива `"use strict"` — рантайм. Модуль даёт оба мира: файл и так JS-strict, плюс вы включаете TS-strict отдельно.

`noImplicitThis` ближе к духу JS-strict: голый this без типа — ошибка компиляции.

Что сказать на собеседовании: модули/классы уже strict. Главное — this не глобал, нет неявных глобалов, нет with, дублей параметров и callee. Это предсказуемость, не скорость.

---

### 39. IIFE, блочная область, module scope

О чём речь: три поколения «спрятать имена». Зачем `(function(){})()`, чем блок лучше `var`, чем модуль лучше обоих. Часто спрашивают в связке с историей языка.

---

#### IIFE

Immediately Invoked Function Expression — выражение-функция, которое **сразу вызывают**:

```js
(function () {
  var secret = 1;
  // ...
})();

secret; // ReferenceError
```

Скобки вокруг `function` нужны, чтобы это было **выражение**, не объявление `function` (объявление нельзя сразу `()` в том же виде). Варианты: `!function(){}()`, `void function(){}()`, `(() => { ... })()`.

Зачем: у `var` нет блока. Единственная изоляция — функция. Бандлы 2010-х: каждый файл в IIFE, чтобы не писать в `window`. Снаружи отдают API `return { ... }` — модульный паттерн (п. 33).

`this` внутри IIFE: в strict/`(() => {})()` — не window; у ordinary IIFE в sloppy — часто глобал. Стрелочный IIFE this берёт снаружи.

---

#### Блок `{ }`

С `let` / `const` / `class` блок сам по себе область:

```js
{
  let x = 1;
}
console.log(x); // ReferenceError
```

`if`, `for`, `while`, `switch`, голые скобки — все дают блок. `var` **игнорирует** блок и живёт в функции.

`try/catch`: параметр `catch (e)` — своя область `e` (не протекает ниже, в современном JS).

Для одноразовых имён внутри функции блок достаточен, IIFE не нужен:

```js
{
  const tmp = compute();
  use(tmp);
}
```

---

#### Module scope

Файл — модуль, если есть `import`/`export` или пакет `"type": "module"` / расширение `.mjs`.

Свойства:

- все top-level имена закрыты в файле;
- наружу только `export`;
- `import` — live binding: экспорт изменился, импорт видит новое (не копия на момент импорта);
- циклы `a import b import a` возможны, значения могут быть в TDZ, пока модуль не доинициализировался;
- top-level `this` — `undefined`;
- top-level `await` разрешён (модуль становится async с точки зрения загрузки);
- `var` не попадает на `window`.

Скрипт (классический `<script>` без type=module): top-level `var` и `function` — на глобал, файлы делят одно пространство, легко столкнуть `function init()`.

---

#### Что брать сегодня

| Задача | Инструмент |
|---|---|
| изоляция файла | ES-модуль |
| локальное имя внутри функции | блок + `let`/`const` |
| легаси без модулей, скрыть var | IIFE |
| публичное API + скрытое состояние в одном выражении | IIFE-модуль или просто модуль |

В TypeScript файл без import/export — **script**, видит глобалы. Случайный глобальный `interface` мержится. `export {}` делает файл модулем: глобалы сами не приезжают, `declare global` нужно явно.

Что сказать на собеседовании: IIFE — функция как единственная область во времена var. Блок закрывает let/const. Модуль — нормальная изоляция файла, верхний this пустой, нет протечки в window.

---

### 40. Temporal Dead Zone в классах и полях

О чём речь: в классах «ещё рано трогать» бывает не только у `let` выше по файлу. Порядок полей, `super` и вызов методов из конструктора дают баги, похожие на TDZ: поле уже «существует как слот», но инициализатор ещё не бежал.

---

#### Порядок при `new` (без extends)

1. Создать объект, прототип — `Child.prototype`.
2. Проставить **поля экземпляра** сверху вниз (`name = "A"`, `#x = 1`).
3. Выполнить тело `constructor`.

Поэтому в конструкторе поля уже обычно видны. Но **порядок полей** важен:

```js
class A {
  a = this.b; // undefined: b ещё не инициализировали
  b = 1;
}
```

`a` читает `this.b` до строки `b = 1`. Не ошибка TDZ как у let (часто просто `undefined`), смысл тот же: порядок инициализации.

---

#### С extends — super первым

В derived-классе до `super(...)` **нельзя** обращаться к `this` — ReferenceError. Сначала должен отработать родитель.

Порядок `new Child()`:

1. Войти в конструктор Child, ещё без `this`.
2. `super(args)` → целиком конструктор Parent (его поля + его constructor).
3. Поля **Child**.
4. Остаток конструктора Child.

Ловушка: Parent в конструкторе вызывает метод, который Child **переопределил**:

```js
class Parent {
  value = 1;
  constructor() {
    this.hello();
  }
  hello() {
    console.log("parent", this.value);
  }
}

class Child extends Parent {
  value = 2;
  hello() {
    console.log("child", this.value);
  }
}

new Child();
// child 1   — вызвали hello ребёнка, но поле Child ещё не ставили (шаг 3 впереди)
```

Печатается `1` (значение Parent) или `undefined`, если у Parent поля не было. Не `2`. Запрет: не звать overridable методы из конструктора.

До `super()` даже не прочитаешь `this.value`. После `super()`, но до полей Child — видишь состояние родителя.

---

#### Статика

Статические поля бегут **когда объявляют класс**, сверху вниз, один раз.

```js
class A {
  static x = 1;
  static y = this.x + 1; // 2, this здесь класс A
  static z = this.w;     // undefined, w ниже
  static w = 3;
}
```

Обращение к `A` во время инициализации статики может увидеть незаполненные поля. Зависимость только сверху вниз.

---

#### Private fields

`#id` ставится по тем же правилам полей. Это настоящий слот в рантайме (не только TS). Parent **не видит** `#id` ребёнка. Доступ к `#x` до инициализации поля в том же классе может дать ошибку (TDZ для private).

`private id` в TypeScript без `#` — только компилятор; в JS поле обычное.

---

#### TypeScript emit

Флаг `useDefineForClassFields` и `target`: поля как `Object.defineProperty` (как в спеке) или как `this.x =` в конструкторе. От этого зависят:

- попадёт ли поле в `for…in`;
- перезапишет ли поле значение, которое положил родитель в конструкторе;
- `declare x: number` (только тип, без emit).

На собеседовании достаточно: поля пишутся в объект в фиксированном порядке относительно `super`, это не декорация типов.

Что сказать на собеседовании: derived — сначала super (и поля родителя), потом поля ребёнка, потом его constructor. Не вызывать из конструктора методы, которые переопределит наследник. Порядок полей в теле класса имеет значение.
